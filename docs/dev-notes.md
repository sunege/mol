## コマンドの詳細

```bash
npm run dev          # Vite 開発サーバ (5173)
npm run build        # tsc -b && vite build → web/dist
npm test             # vitest (web)
npm run build:wasm   # scripts/build-wasm.sh → web/src/wasm/（生成物はコミットする。出荷されるのは CI（Linux）が作り直したもの）
cargo test           # dft-core / dft-wasm
cargo run --release --example profile -- benzene --optimize   # ネイティブの所要時間の内訳
```

WASM の中でどこに時間が行っているかは、関数名を残したビルドを Node で CPU プロファイルに
かけて見る（`dft-wasm` の Cargo.toml に `profiling` プロファイルがある。生成物は
`web/src/wasm/` とは別の場所に出すこと）:

```bash
wasm-pack build crates/dft-wasm --profiling --target nodejs --out-dir /tmp/wasm-prof
node --cpu-prof --cpu-prof-interval 500 bench.cjs   # require('/tmp/wasm-prof/dft_wasm.js') して optimize() を呼ぶだけの小さなスクリプト
```

`.cpuprofile` の `nodes[].callFrame.functionName` と `samples` を数えれば自己時間の表になる。
WASM の内訳は**ネイティブとまるで違う**（P6 のメモ参照）ので、WASM の高速化はネイティブの
`sample`/プロファイラだけ見て決めないこと。

前後の所要時間の比較も Node（`--target nodejs` の release ビルド）で取るのが安定する。
CLAUDE.md が指しているのはこのコマンド:

```bash
wasm-pack build crates/dft-wasm --release --target nodejs --out-dir <scratch>
# あとは require('<scratch>/dft_wasm.js') して scf() / optimize() を呼ぶだけの小さなスクリプト。
# 複数の Worker で同時に回して測るなら node の worker_threads（P10-1 でそうした）。
# nodejs ターゲットのグルーは wasm を module.exports に出さないので、線形メモリの大きさを
# 見たいときは出力の末尾に `module.exports.__wasm = wasm;` を足す（生成物なので scratch 側で）。
```

Chromium と同じ V8 で、しかも間引かれない。Claude の Browser ペインは**非表示だと
ワーカーが間引かれ**（レンダラの CPU が 30〜50% に落ちていた）、同じバイナリで Node の
1.2〜1.8 倍かかった。長い計算ほど歪むので、ペインが見えていないときのブラウザ実測は参考値。

参照値・基底データの再生成（PySCF が要る。普段は不要で、基底や汎関数を変えるときだけ）:

```bash
python3 -m venv .venv && .venv/bin/pip install pyscf
.venv/bin/python scripts/gen_reference.py
```

`main()` の全実行は分〜十数分かかる（ベンゼンを grid level 9 で解くため）。
一部だけ要るときは関数を直接呼ぶこと。放置すると孤児プロセスとして残り続ける:

```bash
.venv/bin/python -c "import sys; sys.path.insert(0,'scripts'); import gen_reference as g; g.open_shell_reference()"
```

## 規約の詳細

- **単位**: エンジンは原子単位（Bohr, Hartree）、UI は Å。変換は `crates/dft-wasm` の境界 1 箇所だけ。エンジン内部に Å を持ち込まない。
- **`dft-core` に wasm 依存を入れない。** 全ロジックをホスト上の `cargo test` で検証できる状態を保つ。
- **Rust を書き戻すときに `mv`（や `cp -p`）を使わない。** cargo の再ビルド判定は
  mtime で、バックアップから `mv` で戻すと**ファイルの時刻ごと巻き戻る**ので
  cargo は「変更なし」と判断して再コンパイルを飛ばす。`wasm-pack` は成功したように
  見え、**中身は前のままの `.wasm` が `web/src/wasm/` に書かれる**。
  一度これで、検証用に 2 秒へ縮めたタイムアウトを 300 秒へ戻したつもりのまま
  2 秒のバイナリを配信し、「タイムアウトが厳しすぎる」という報告を受けた。
  戻すときは `cp`（`-p` なし）か、戻したあとに `touch` すること。
  疑わしいときは**定数がバイナリに入っているか直接見る**のが早い:
  `python3 -c "import struct,pathlib; w=pathlib.Path('web/src/wasm/dft_wasm_bg.wasm').read_bytes(); print(w.count(struct.pack('<d', 1800000.0)))"`
- **`web/src/wasm/` はコミットする。** Vercel のビルド環境に Rust ツールチェーンが無いため。CI は main への push でも PR でも Linux で作り直し、コミットされたものとバイトが違えばそのブランチに「chore: rebuild WASM artifact」をコミットする（フォークからの PR だけは push できないので失敗させる）。push のあとは bot のコミットを `git pull` で取り込むこと。
- **π/σ の判定は対称性であって経験則ではない。** 分子平面での鏡映は Kohn-Sham 演算子と
  可換なので、各軌道は厳密にその固有関数になる（ベンゼンで ⟨σ̂⟩ = ±1.000000）。
  判定は基底での反射行列 U を作って `Cᵀ S U C` の対角を見る。U は単項式を展開して
  作っているので任意の角運動量で動く（6-31G* の d 関数でも書き換え不要）。
  **3 原子は必ず平面なので平面性は何も言っていない**。`MIN_ATOMS_FOR_A_PLANE = 4`
  はそのための下限で、水が「π＝面外孤立電子対」として扱われるのを防いでいる。
- **テストの参照値も物理定数テーブルも記憶から書かない。** 一度これで誤った定数を書いてテストが落ちた。次のどちらかにする:
  1. テスト内で独立な経路から導出する（例: 核間反発を「ペア距離を書き下した和」と比較する、Boys 関数を Simpson 積分と照合する）
  2. `scripts/gen_reference.py` で生成して JSON / 生成 .rs としてコミットする
  STO-3G 係数と Lebedev グリッドも同スクリプトの生成物であり、手で編集しない。
  唯一の例外は `xc/lda.rs` の VWN5 フィッティング定数（汎関数の定義そのもの）で、
  これは `tests/reference_xc.rs` が libxc と 1 点ずつ照合して守っている。
- **参照値が合わないとき、先に「どちらが正しいか」を確かめる。** 低密度・完全スピン分極の
  領域では VWN5 の式が桁落ちし、libxc の側が 1e-10 ずれる。50 桁演算で確認済みで、
  `tests/reference_xc.rs` にその許容と理由を書いてある。
- **非収束は例外ではなく戻り値**（要件 F5）。SCF・構造最適化とも最大反復数とタイムアウトを
  持ち、例外を投げずに状態を返す。ただし**「解けなかった」と「間に合わなかった」は区別する**:
  - **SCF が収束しない**（単点計算の `converged: false`、最適化の `OptStatus::ScfFailed`）
    ＝その原子配置には束縛された電子状態が無い。**発散アニメーション**を出し、
    **エネルギーも反復数も等値面も出さない**（すべて `—`）。最後の反復の密度は
    「その分子の密度」ではなく「反復が止まらなかった最後の 1 枚」なので描かない。
    画面で起きることは原子が飛び散って戻ってくることだけで、それが答えの全部。
  - **最適化が時間切れ・回数上限で止まった**（`Interrupted` / `MaxSteps`）＝
    分子は何も失敗していない。通った構造すべてで電子は解けている。**静かに止め、
    そこまで緩和した構造をそのまま残す**。その構造の SCF は収束しているので
    エネルギーも反復数も等値面も出す。止まった理由（「時間切れ」「回数の上限」）は
    画面に出す — 計算機の都合であって DFT パラメータではないので要件 F4 に触れないし、
    黙っていると途中の構造が完成品に見えてしまう。もう一度押せばそこから続きが走る。

  **発散させてよいのは前者だけ。** 後者を飛び散らせると「計算機が遅かった」を
  「この分子は存在できない」と言い換えることになる。判定は `protocol.ts` の
  `hasUsableStructure()` が唯一の情報源。UI 側のゲートは 2 つあり、
  `solved`（電子が解けたか＝数値と等値面を出してよいか）と
  `settled`（構造が落ち着いたか＝「完了」と言ってよいか）は別物。
- **DFT パラメータを UI に出さない。** 基底関数・電荷・スピン多重度は自動決定（要件 F4）で、ユーザーには見せない。
  `ScfOutcome` の `multiplicity` / `charge` / `attempts` は**診断用**で、画面に出さない
  （dev ビルドの Worker が `console.debug` に 1 行出すだけ）。P5 が最適化中にスピン状態を
  固定するのにも使う。
- **スピン状態の探索は「両方解いて比べる」しかない。** HOMO-LUMO ギャップで
  三重項を試すかどうかを振り分けたくなるが、**使えない**。実測（`scf::run_*` で直接測定）:
  ベンゼンはギャップ 0.226 Ha で一重項、CH₂ はギャップ 0.160 Ha で**三重項が 0.186 Ha 下**。
  順序はギャップで決まらないし、そもそも一重項が収束しない系ではギャップ自体が無い。
  **三重項を収束した一重項の密度から始めるのも遅くなる**（P6 で実測: 同じエネルギーに
  着くのに H₂O 7 → 15 反復、CH₄ 14 → 26 反復）。level shift も遅くなるうえ、ベンゼンの
  Fine グリッドでは別の、0.027 Ha 高い三重項に落ちた。探索を安くする手はグリッドのほうで、
  状態は Medium で選び、勝った状態だけを最適化用の Fine で解き直す
  （`driver::solve_then_refine`。Coarse / Medium / Fine で全テスト分子が同じ状態を選ぶ）。
- **勾配は Hellmann-Feynman だけでは足りない。** 基底関数が原子核に乗っているので、
  1 電子・2 電子のすべての積分に「基底が動く」分の微分（Pulay 項）がある。全体は
  `Σ D ∂H/∂R + ½ΣΣ DD ∂(μν|λσ)/∂R + ∂E_xc/∂R + ∂E_nn/∂R − Σ W ∂S/∂R`
  で、`W` はエネルギー重み付き密度行列。**この式は SCF が収束しているときにしか成り立たない**
  （途中の密度で勾配を取っても何の微分でもない）。
- **`nalgebra` の `SymmetricEigen` は使わない。** 0.33 は、この engine が作る
  Kohn-Sham 行列に対して**固有値と固有ベクトルの対応が壊れた**分解を返すことがある
  （`V L Vᵀ` が入力と 0.64 ずれる。直交性も固有値も正しいので黙って通る）。
  P2〜P4 が気づかなかったのは、**占有軌道どうしの混ざりは密度を変えない**から。
  勾配は気づく: `W` は軌道ごとにエネルギーで重みを付けるので、混ざった瞬間に
  Pulay 項が壊れる。`scf/linalg.rs` は Jacobi 法を自前で回している（36×36 なら
  XC のグリッド 1 回分より遥かに安い）。検査は「`A V = V Λ` と `V L Vᵀ = A` を見る」こと。
  固有値だけ・直交性だけを見るテストはこのバグを通す。
- **XC のグリッド重みの微分は省いている。** つまり解析的勾配は「**グリッドを固定した**
  エネルギー」の厳密な微分。検証もそれに合わせる:
  `System::build_with_grid` でグリッドを止めたまま中心差分を取れば 1e-6 で一致する。
  グリッドを毎回作り直す差分と比べると、省いた分が見える（歪んだ水で実測）:
  **Coarse 4.3e-4 / Medium 7.2e-5 / Fine 1.2e-5 Ha/Bohr**。収束判定の 4.5e-4 に対し
  Coarse は論外なので、**構造最適化は `opt::OPTIMIZER_GRID`（Fine）で回す**。
  設計計画の「グリッドを細かく取って実害がないことを確認する」がこれ。
- **ERI 微分は密度を先に Hermite 係数へ畳み込む。積分そのものは作らない。**
  `Σ D_μν D_λσ ∂(μν|λσ)` にしか使わないので、`Ē_tuv = Σ D_μν E^{μν}_tuv` を先に作れば
  原始四重項ごとに R 1 枚と小さな行列ベクトル積 2 回で 12 方向ぶんが出る（`DensityPair`）。
  `two_electron_gradient_by_quartets`（テスト専用）が「全部の微分積分を作ってから縮約する」
  素朴な版で、速い版はこれと 1e-12 で一致することを確かめている。4 中心はいまも全部明示的に
  微分している（並進不変性で 1 つを出しても dot 3 回分しか得をせず、テストが自明になる）。
- **シェルは「群」で扱う。** 同じ原子・同じ指数の殻（STO-3G の 2s と 2p）は Gaussian 積も
  R も同じなので、ERI・ERI 微分・格子上の基底評価はすべて `BasisSet::groups()` 単位で回る。
  炭素の価電子四重項は R 16 枚が 1 枚になった。基底を差し替えても自動でまとまる（6-31G の sp 殻も）。
- **グリッドの点の並び順には意味がある。** `grid::build` は点を再帰二分割で並べ替え、
  先頭から `grid::BLOCK`（128）点ずつが空間的にまとまった塊になるようにしている（分割位置を
  128 の倍数に置くので、ブロックが葉をまたがない）。XC はブロック単位で「どの点からも
  無視できる基底関数」を落とすので、並びを崩すと答えは同じまま遅くなる。生成順（原子ごと・
  球殻ごと）ではブロックが球殻の帯になって分子をまたぐ。Morton 曲線順でも外側の疎な点で
  ブロックが数十 Bohr に広がり、落とせた値は 12%。再帰二分割で 26% になった（ベンゼン Fine）。
- **スクリーニングは上界で判定する。「たぶん小さい」で落とさない。** `xc::blocks::SCREENING`（1e-14）は
  ブロック内のどの点でも値（勾配計算では微分も）がそれ未満だと**証明できる**殻群だけを落とす。
  `nothing_above_the_threshold_is_ever_left_out` が全点でそれを確かめ、
  `screening_changes_nothing_that_matters` がエネルギー・ポテンシャル・勾配を閾値 0 の場合と 1e-12 で比べる。
  ERI の原始対の切り捨て（`NEGLIGIBLE_PRIMITIVE_PAIR` = 1e-22、`exp(−μR²)` が倍精度で消える対）も同じ考えで、
  微分した対とそうでない対で**同じ原始対を残す**こと（`DensityPair` は原始対の番号で両者を対応させている）。
  ERI 微分の原始四重項単位の切り捨ては P6 で調べたが、手頃な見積もりが上界にならなかった
  （実際の寄与が見積もりの 2.2 倍になる四重項があった）ので入れていない。
- **SCF は格子上の基底値（`xc::BasisOnGrid`）を 1 回作って反復で使い回す。**
  ベンゼンの Fine で約 30 MB で、SCF が返れば捨てる。`System` には持たせない
  （最適化中は新旧 2 つの `System` が同時に生きるので倍になる）。
- **ブラウザ版は WebAssembly SIMD を前提にする**（`.cargo/config.toml` の `+simd128`、
  wasm-opt の `--enable-simd`）。SIMD の無いブラウザではモジュールがコンパイルできないので、
  **起動時に `engineSupport.ts` の 43 バイトの判定モジュールを `WebAssembly.validate` にかけ、
  非対応なら Worker を作らずに案内を出す**（P7 でユーザーが「非 SIMD 版を並べて配る」より
  こちらを選んだ）。アプリ全体の下限は **Chrome / Edge 96・Firefox 114・Safari 16.4**
  （webassembly.org の機能表と MDN の互換データで確認。Chrome は reference-types、
  Firefox はモジュール Worker で決まり、SIMD が効いているのは Safari だけ）。
  判定モジュールは wasm-opt で「SIMD 有効なら妥当、MVP のみなら拒否」を確かめてある。
  **Worker の初期化失敗も黙らせない**: Worker は `ready` の代わりに `unavailable` を送り、
  `ready` 前の `onerror` も同じ扱いで、`workerClient` は保留中も以後もすべての要求を
  `EngineUnavailableError` で失敗させる（P6 までは `ready` を永久に待ち、画面が空の周期表の
  まま黙って固まっていた）。
- **出荷される `.wasm` は CI（Linux）が作ったもの。Mac のビルドとはバイトが一致しない。**
  P7 で「どこでも同じバイト」にしたつもりが、確かめたのは macOS の中だけだった。最初の CI が
  作り直した版（`f3b6eb3`）は、サイズ・文字列・命令列は同じで、データ領域でパニック位置の
  記録（16 バイト）の並び順が違い、それを指す `i32.const` が 39 箇所違っていた。機能は同一
  （両方でベンゼンを最適化してエネルギー小数 10 桁・歩数・最大力・進捗の段階まで一致）。
  原因は推定で、cargo がクレートごとに作るハッシュに、ホスト向けにビルドされる proc-macro
  （serde・wasm-bindgen のマクロ）経由でホストの違いが入り、リンク時の並びが変わるのだと
  考えている。安定版の cargo で揃える手段は無い。だから CI は比較して落とすのではなく、
  作り直してコミットする（上の規約）。同じ OS の中で一致させるための手当ては残してある:
  1. 依存 crate のパニック位置に `CARGO_HOME` の絶対パスが入る（P6 までの成果物には
     `/Users/konya/.cargo/registry/...` が 13 箇所あった）。`scripts/build-wasm.sh` が
     `--remap-path-prefix` で `/cargo` に置き換える。cargo の `trim-paths` は 1.98 ではまだ unstable。
  2. 標準ライブラリのパスに rustc のコミットが入る → `rust-toolchain.toml` と CI で 1.98.1 に固定
     （固定しないと Rust のリリースのたびに CI が成果物を作り直してコミットする）。
  3. wasm-opt の版は wasm-pack が決める → CI の wasm-pack を 0.15.0 に固定。
  macOS 上で「別ディレクトリへのコピー + 空の `CARGO_HOME`」から作り直すと 5 ファイルとも一致する。
  **コメントだけの Rust の変更でも生成物は変わる**（P10 で踏んだ）。理由は 2 つあって、
  どちらも「機能は同じなのに CI が作り直してコミットする」形になる:
  1. **wasm-bindgen は公開関数の doc コメントを `.d.ts` と `.js` に写す。** `optimize` の doc を
     直しただけで両方が変わった。
  2. **行が増えるとパニック位置の行番号が動く。** doc を 5 行増やしたら `.wasm` の 3 バイトが
     `542 → 547`（`0x21e → 0x223`）に変わった。差はこの 3 バイトだけで、命令は 1 つも違わない。
  だから「コメントなら CI は何もしないはず」と考えないこと。**push したら `git pull`** の規約は
  このためにもある。
  **rustflags は `RUSTFLAGS` で渡さない。** `.cargo/config.toml` の `+simd128` を置き換えて
  しまい、SIMD 無しのバイナリが黙ってできる（`--config` で渡した配列は連結される）。
  空の `CARGO_TARGET_WASM32_UNKNOWN_UNKNOWN_RUSTFLAGS=""` は上書きにならず無視される（実測）。
- **Vercel の Root Directory はリポジトリ直下（空）にする。** 設定は直下の `vercel.json`
  （`npm run build` → `web/dist`、`.wasm` の Content-Type、`/assets` の immutable キャッシュ）で、
  Root Directory が直下でないと読まれない。P7 の最初のデプロイは Root Directory が `web` より
  下になっていて、`npm` が上の `web/package.json` を見つけてビルドし `web/dist` を作ったのに、
  Vercel は Root Directory の下の `dist` を探して「No Output Directory named "dist"」で落ちた。
  直下なら `vercel.json` がダッシュボードの Override より優先される（手元で確認）。
  正しい構成のログには `> mol@0.1.0 build` → `> npm run build --workspace web` が出る。
- **Vercel のビルドは手元で再現できる（ログイン不要）。** リポジトリを別の場所に clone し、
  `.vercel/project.json` に `{"projectId":"x","orgId":"y","settings":{"rootDirectory":…,
  "framework":…,"installCommand":…,"buildCommand":…,"outputDirectory":…}}` を書いて
  `npx vercel@<ログに出ている版> build --yes` を走らせる。ログの形（「Running "install" command」
  が出るか、`> mol@0.1.0 build` が出るか）で設定の上書きの有無まで見分けられる。
- **性能は同じ条件で前後を並べて測る。** このマシン（i5-5287U）のネイティブ計測は同じバイナリでも
  ±30% ぶれるので、判断は複数回の最小値か、`sample` / CPU プロファイルの比率で行う。
  WASM は内訳がネイティブと違う（ネイティブで速い `gemm` や `exp`・`cbrt` が WASM では
  ソフトウェア実装になる）ので、WASM の改善は WASM のプロファイルで決める（コマンド節）。
- **勾配を書き換えたら、まず項ごとの有限差分を見る。** `integrals/deriv.rs` のテストは
  ∂S・∂T・∂V・∂ERI を**それぞれ**行列ごと中心差分と比べている。全体の勾配だけ見ていると
  「どこが悪いか」が出ない。並進不変性（全原子の勾配の和 = 0）は ∂V の Hellmann-Feynman 項を
  単独で捕まえるので、必ず残しておくこと。4 中心すべてを明示的に微分しているのは、
  1 つを並進不変性から逆算するとこの検査が自明になるため。
- **Worker の契約は `protocol.ts` が唯一の情報源。** 失敗は例外を越境させず `error` レスポンスで返す。
- **Worker のレスポンスは「1 リクエスト = 1 応答」ではない。** 構造最適化は受理した構造ごとに
  `step` を返し、最後に `scf` で終わる。一点計算も最適化も、作業の段階が変わるたびに
  `progress` を返す。どれが終端かは `protocol.ts` の `isTerminal()` が唯一の
  情報源で、`workerClient` はそれを見て `#pending` から消すかどうかを決める。
  `step` と `progress` は `onPartial` に流れるだけで Promise を解決しない
  （`workerClient.test.ts` が偽の Worker を通して往復で確かめている）。
- **進捗の段階名は「何に時間を使っているか」であって「何を試しているか」ではない**（F4）。
  `preparing`（積分・グリッド）/ `searching`（電子の並び方＝スピン探索と Fine での解き直し）/
  `forces`（step の力）/ `solving`（step の電子）の 4 つだけで、試している状態・試行回数は
  境界を越えない。名前は `dft-wasm` の `mod stage` と `protocol.ts` の `progressFromEngine()` の
  2 箇所に書かれていて、後者は知らない名前を黙って捨てる。ずれると進捗カードが止まるだけで
  どこも落ちないので、`engine.test.ts` がコミット済みの `.wasm` を実際に呼んで照合している。
  文言は `components/progress.ts` で、テストが全状態を列挙して DFT パラメータの語が出ないことを見る。
- **`opt::relax` の `on_stage` は聞くだけ。** 戻り値は無く、結果に影響しない。`dft-core` に
  時計は入れない（経過時間は UI が `performance.now()` で数える）。
- **アニメーション中は viewer の所有権が `FramePlayer` にある。** App の `animation`
  （`'divergence' | 'optimization' | null`）がそのフラグで、null のときだけ
  `setMolecule(atoms)` する。**Player がキューを使い切っても終わりとは限らない**:
  最適化中は「次のステップを計算中」なだけなので、`producerDoneRef` が立つまで
  `onIdle` は何もしない。
- **緩和後の構造は「答え」なので、アニメーションを待たずに即 `setAtoms` する。**
  バックグラウンドのタブでは `requestAnimationFrame` が**まったく走らない**ので、
  Player の完了を待って commit すると「パネルは完了と言っているのに `atoms` は
  ユーザーが作った元の構造のまま」になり、次の編集で `stopAnimation()` が
  結果を黙って捨てる。実際に踏んだ（2 回目の「安定な形にする」がプリセットから
  やり直しになり、エネルギーが上がって見えた）。Player は**表示の所有権を返すだけ**で、
  何を残すかは決めない。発散は絵なので `atoms` を触らない。
- **キャンセルは `worker.terminate()` + 再生成**（`workerClient.ts`）。単一スレッド WASM は外から中断できないため。
- **Viewer はメッシュを再利用する。** 毎フレームのジオメトリ生成に戻さない。P5 の最適化アニメーションが同じ経路を毎フレーム叩く。
  等値面だけは頂点数が閾値ごとに変わるので `BufferGeometry` を作り直すが、`Mesh` と
  マテリアルは使い回し、古い geometry は必ず `dispose()` する（GPU バッファは GC されない）。
- **marching cubes の 256 ケース表を書き写さない。** `marching.rs` は定義から導出している
  （面ごとに切断辺を結び、閉ループにし、符号だけから向きを決める）。公開されている表は
  曖昧面の解消方法を固定した「選択」を含んでいて、1 エントリの写し間違いが穴になり、
  エネルギーのテストでは絶対に捕まらない。テストは全 256 ケースの被覆と、球・二球・
  乱数場に対する閉曲面性（有向辺が往復で打ち消し合うこと）と体積・面積で押さえている。
- **等値面メッシュの閉曲面性はループ境界で見る。** ループは扇状に三角形化するので、
  内部対角線は隣のキューブの対角線と一致して 4 枚に共有されることがある。穴ではない。
  「無向辺がちょうど 2 枚」ではなく「有向辺が往復で打ち消し合う」で検査すること。
- **アニメーションはキーフレーム列 + `FramePlayer`。** 発散演出も P5 の最適化ステップも
  `web/src/animation/` の同じ経路を通る。Player は表示レート（rAF）と生成レートを分離し、
  アンカー時刻を 1 フレーム分ずつ進めるので、コールバックが遅れても尺がずれない。
  時計とスケジューラは注入するので、ブラウザ無しでテストできる。
- **`renderer.setSize(w, h)` の第3引数を `false` にしない。** CSS サイズが書かれず、Retina で canvas が 2 倍の大きさになりパネルを覆う（実際に踏んだ）。

## 要件定義書に対する技術的な補足

1. **「Hellmann-Feynman 力」だけでは力が求まらない。** 原子核上に中心を持つガウス基底では基底関数自体が原子位置に依存するため、Pulay 項（`-Σ W_μν ∂S_μν/∂R` ほか）を含む完全な解析的勾配が必要。
2. **COOP/COEP によるマルチスレッド化は最終フェーズの任意項目。** `wasm-bindgen-rayon` は nightly + `-Z build-std` 依存。まず単一スレッド + WASM SIMD（stable）で性能目標を狙う。

## フェーズの記録

### P5 の実装メモ

- **有限差分ハーネスを勾配より先に書いた**（設計計画どおり）。`gradient/finite_difference.rs`。
  最初にそれ自身を「既に正しいと分かっている唯一の勾配」= 核間反発で検証している。
- **項ごとに中心差分と比べるのが効いた。** ∂S・∂T・∂V・∂ERI をそれぞれ行列のまま
  比較したので、最初の実装で全部が一発で通った。通らなかったのは**全体**だけで、
  そこから `nalgebra` の固有値分解に辿り着いた（上の規約を参照）。
  項ごとのテストが無ければ「勾配のどこかが 3 倍おかしい」で止まっていた。
- **ガウス関数の中心微分は 1 つの恒等式に尽きる**:
  `∂/∂A_x φ(i,j,k) = 2a φ(i+1,j,k) − i φ(i−1,j,k)`。
  微分した積分は「角運動量をずらした普通の積分」なので、ERI 側は
  `ShellPair` の Hermite 係数を作り替えるだけで既存の `quartet()` がそのまま使える。
  新しい積分カーネルはひとつも書いていない。d 殻でも動く（テスト済み、6-31G* 用）。
- **探索の結果をそのまま最適化の 0 歩目に渡している。** 探索は初期構造で
  1 回だけ走り、決まった状態を `opt::relax` が固定して回す。SCF は 1 回分節約できる。
  収束しなかった結果を渡すと `opt::relax` は何も動かさずに `ScfFailed` を返す（F5 の経路）。
  P6 から探索は Medium グリッドで行い、勝った状態だけを Fine で解き直して渡す
  （`driver::solve_then_refine`。P6 のメモ参照）。
- **各ステップの SCF は前ステップの密度から始める**（`InitialGuess::Previous`）。
  収束しなければ 1 度だけ SAD からやり直す。水で 6 反復→ 3〜4 反復になる。
- **PySCF 側の参照は scipy の BFGS で作った。** geomeTRIC も pyberny も入っていないので、
  `gen_reference.py` の `relaxed_geometry()` が PySCF のエネルギーと解析的勾配を
  `scipy.optimize.minimize` に渡している。別のエンジン × 別の最小化アルゴリズムなので、
  一致すれば「同じ極小点を 2 通りの方法が見つけた」ことになる。
  PySCF の DFT 勾配も既定で `grid_response = False`（＝こちらと同じ近似）なので、
  比較しているのは同じ量。ずれは実測で水 1.5e-6 / メタン 1.2e-5 Ha/Bohr。
- **`wasm-pack` 0.15 は自分が吐いた `web/src/wasm/package.json` を読み返して落ちる**
  （`files` が配列なのに文字列を期待する）。`npm run build:wasm` は先に消してから走らせる。
- **生成物が本当に更新されたかを疑うこと**（上の mtime の規約）。ブラウザでの挙動が
  ソースと食い違ったら、まず `.wasm` の中に定数が入っているかを見る。

### P5 の実測

ネイティブ（release）。勾配 1 回の内訳:

| | System::build | SCF | 勾配 1e | 勾配 2e | 勾配 XC |
| --- | --- | --- | --- | --- | --- |
| H₂O (Fine) | 14 ms | 248 ms | 0.5 ms | **160 ms** | 90 ms |
| CH₄ (Fine) | 26 ms | 313 ms | 1.0 ms | **227 ms** | 103 ms |
| ベンゼン (Medium) | 4.1 秒 | 1.8 秒 | 48 ms | **72.8 秒** | 0.9 秒 |

小さい分子では勾配 1 回 ≈ SCF 1 回。**ベンゼンでは ERI 微分だけで SCF 全体の 40 倍**になる。
理由は単純で、ユニークなシェル四重項ごとに 4 中心 × 3 方向 = 12 回 `quartet()` を
呼び、しかも片側の角運動量が 1 つ上がっているため 1 回あたりも約 2 倍高い。

ブラウザ実測（release + wasm-opt -O3、Fine グリッド。初回のスピン探索込み）:

| | 所要 | ステップ数 | 収束後のエネルギー |
| --- | --- | --- | --- |
| H₂O | 3.9 秒 | 4 | −74.743110 Ha（PySCF −74.743109） |
| CH₄ | 6.5 秒 | 3 | −39.617132 Ha（PySCF −39.617139） |
| O₂ | 6.3 秒 | 5 | −147.205416 Ha（三重項のまま固定） |
| NH₃ | 7.5 秒 | 7 | −55.296302 Ha |
| **ベンゼン** | **1 歩 60〜110 秒**（0 歩目 133 秒、以降 111 秒 → 61 秒） | 収束に 15 歩前後 | 未実測 |

**ベンゼンは 15〜25 分かかる**（P5 時点。P6 で約 16 秒になった。P6 の実測参照）。
`OPTIMIZE_BUDGET_SECONDS`（`dft-wasm`）が 1800 秒なのはそのため — スコープが上限として挙げている分子が 1 回のボタンで終わらないのはおかしい。
この予算は**ステップとステップの間でしか見ないので、固まった計算は捕まえられない**。
止める手段はユーザーの「中止」（`worker.terminate()`）のほうで、予算は放置されたタブが
走り続けるのを防ぐ最後の歯止めにすぎない。**縮めると健全に進んでいる計算を切るだけ**になる。
予算に当たったときは途中まで緩和した構造が残り、「時間切れ · N 回動いたところまで」と出る。
もう一度押せばその構造から続く（ただしスピン探索は毎回やり直す。P6 でも残っているが、
探索を Medium グリッドに移したのでベンゼンで約 2 秒）。
歩ごとに速くなっているのは前ステップの密度から始めているから（133 → 111 → 61 秒）。

### P6 の実装メモ

実測で順番を決めた。着手前のネイティブ内訳はベンゼンの ERI 微分 34 秒に対して他はすべて 2 秒未満
（下の表）なので ERI 微分から。そこが 0.6 秒になった時点で「ベンゼンは 3 歩で収束する」
（P5 の見積もりの 15 歩ではなかった）ことと、**Fine グリッドでのスピン探索が全体の半分**で
あることが見え、次はそこ。以降は Node の CPU プロファイル（WASM）で決めた。

- **ERI 微分: 密度を先に畳み込む**（規約参照）。34 秒 → 0.42 秒（ネイティブ、ベンゼン）。
  引き継ぎにあった「R を 1 回にする（1.5〜2 倍）」「4 中心目を並進不変性で（25%）」より
  桁で効く。R を共有するだけでは 12 個の積分ブロックの縮約が残るが、密度を先に入れると
  ブロックそのものが消える。
- **Boys 関数のテーブル化。** T ≤ 20 で 0.05 刻みの表から 7 項の Taylor 展開
  （`dF_n/dT = −F_(n+1)` なので表の中身だけで展開できる）。表は起動時に級数から作る。
  級数とは 1e-14（相対）で一致し、Simpson 積分のテストもそのまま通る。
- **シェル群**（規約参照）と **ERI の原始対の切り捨て**。ERI 本体は 1.6 秒 → 0.31 秒。
- **`HermiteR` の漸化式を次数ごとの手順列に展開**した。どの要素をどの順で埋めるかは
  次数だけで決まるので、4 次元配列の添字計算を 1 回にできる。前のループと**ビット単位で一致**
  （テストあり）。WASM での R の自己時間が 1.54 秒 → 1.12 秒（ベンゼン最適化 1 回分）。
- **XC: 空間ブロック + 上界スクリーニング + SCF 内キャッシュ + 専用カーネル**（規約参照）。
  - 基底評価は 2s/2p で `exp` を共有し、`a r² > 50` の原始は `exp` を呼ばずに 0 にする
    （微分に掛かる 2a とアルゴンの係数を入れても 1e-17 未満）。s・p 殻は一般の単項式を通さない。
  - XC 勾配は `Σ_ν D_μν φ_ν = (Dφ)_μ` を使って行列を作らない形にした（6 本の m×m 積が消える）。
    閉殻は 2 つの同じ半分を回さず 1 チャンネルで計算する。
  - SCF で要るのは各点の ρ だけなので `(Dφ)` 全体ではなく `φᵀDφ` を下三角だけで作る。
    V_xc は対称なので下三角だけ足して鏡映する。
  - **matrixmultiply をやめた理由**: ネイティブでは AVX カーネルで速いが、WASM 用のカーネルが無く、
    汎用フォールバックが **WASM の実行時間の 34%**（Node の CPU プロファイル）を占めていた。XC の積は m（数十）× 128 と
    小さいので、ベクトル化できる形のループ（列方向の要素ごとの更新だけで、和の順序を変えない）を
    書いた。ネイティブでは同等、WASM では大きく速い。
  - LDA は `powf(x, 4/3)` を `x·cbrt(x)` に、定数の立方根を 1 回に、ζ = 0 ではスピン補間を
    評価しない。WASM では `pow`・`cbrt` がソフトウェア実装で、`cbrt` の中のソフトウェア FMA まで
    合わせると LDA の超越関数が 16% あった。libxc との 1e-11 比較はそのまま通る。
- **スピン探索は Medium、最適化は Fine**（`driver::solve_then_refine`）。Fine のまま探すと
  ベンゼンの三重項は 28 反復かかっていた（Medium では 11）。解き直しが収束しなければ
  Fine で探索全体をやり直すので、結果が以前より悪くなることはない。
- **WASM SIMD**（規約参照）。ベンゼン最適化で約 1 割。
- **Becke 重みは原子対ごとに 1 回**: `ν_BA = −ν_AB` で多項式が奇関数なので
  `s(ν_BA) = (1 + g)/2` が同じ評価から出る。サイズ補正 `a_AB` は反対称に作る。

**試して効かなかったもの**（再挑戦しないこと。数字は実測）:

- 三重項を一重項の収束密度から始める → 遅くなる（規約参照）。
- 三重項に level shift → 遅くなり、ベンゼン Fine では高い三重項に落ちる。
- 最適化ステップの SCF（前ステップの密度から開始）でダンピングを切る → ベンゼンは 7/6/6 反復の
  まま。小さい分子で 1 反復減るだけで、難しい系で収束に失敗したときの損（100 反復＋やり直し）が大きい。
- XC のブロックを 64 / 256 点にする → 128 と誤差の範囲。
- ERI 微分の原始四重項の切り捨て → 規約参照（上界にならない）。

### P6 の実測

同じマシン（i5-5287U、2 コア）で、P5 の状態（238fc64 を worktree に展開）と並べて測った。
分子は UI のプリセット（ベンゼンは C–C 1.39 Å / C–H 1.09 Å の理想構造）。

**ネイティブ**（release、`cargo run --release --example profile -- <分子> --optimize` を前後の
ビルドで交互に 2 回ずつ。この機械は ±30% ぶれるので幅で書く）:

| | ERI | SCF（Fine、1 回） | 勾配 2e | 勾配 XC | 最適化 全体 |
| --- | --- | --- | --- | --- | --- |
| H₂O | 5 → 3〜6 ms | 0.17 → 0.06〜0.07 秒 | 90〜100 → 3〜5 ms | 38〜43 → 15〜17 ms | 1.9 → 0.55 秒 |
| CH₄ | 10〜14 → 3〜9 ms | 0.30〜0.32 → 0.11〜0.13 秒 | 240〜250 → 7〜13 ms | 94〜104 → 36〜48 ms | 4.1〜4.6 → 1.1〜1.2 秒 |

### P8 の実装メモ

- **観測モードへの切り替えは計算の開始時**（2026-09-20 ユーザー決定）。当初の合意は「計算が
  終わったら」だったが、計算中に編集モードのままだと誤クリックで計算が中止され、緩和中に値が
  動くのを見せるには計算中から計測できる必要がある。失敗（発散・エラー・中止）で終わったら
  開始前のモードに戻す（計算中にユーザーが自分で変えたときは戻さない）。
- **P8-1 計測（`scene/measure.ts`）**:
  - 角度は `acos(cos)` ではなく `atan2(|u×v|, u·v)`。`acos` は 0°・180° の近くで桁を失い、
    直線分子がちょうどそこにいる。
  - 二面角は `atan2(|b2| b1·(b2×b3), (b1×b2)·(b2×b3))`。IUPAC の範囲は (−180, 180] なので、
    atan2 が −180 を返したら +180 にする（符号付きゼロで実際に起きる。テストに入れてある）。
  - **二面角が「定まらない」とする閾値は、3 点が直線から 1° 以内**（`COLLINEAR_TOLERANCE_DEGREES`）。
    数学的には完全な直線だけが未定義だが、直線に近いと面の向きは端の原子の直線からのずれで
    決まり、それが緩和後の構造の精度より小さくなる。最適化が 179.x° まで伸ばした直線分子で
    二面角が雑音のまま大きく揺れるのを避けた。
  - 表示の丸めで綴りが揺れないようにした: 丸めて 0 なら `-0.0` と書かない、−180 に丸まる
    二面角は `180.0` と書く（アニメーション中にラベルがちらつくため）。
  - テストの期待値はすべて組み立てで作った（Rodrigues の回転で既知の角度に置き、ランダムな
    剛体運動で動かす）。**符号は独立に 2 通りで確かめた**: (1) 組み立て（b→c 軸まわりの右ねじ回転）、
    (2) IUPAC の文言どおりの Newman 投影（b から c を見る視点の画面座標で、前の結合を時計回りに
    回して後ろの結合に重ねる角度）。加えて、逆順で同じ値・鏡像で符号反転。
  - 計測する原子の選び方（`toggleMeasured`: もう一度で外す、5 個目はそこから選び直し）も
    純関数としてここに置いた。
- **P8-2 操作の解釈（`scene/gestures.ts`）**: `pressAction`（押した瞬間: 原子のドラッグか回転か）・
  `clickAction`（動かさずに離した: 配置・隣接配置・選択・計測・何もしない）・`keyAction`
  （Delete/Backspace・Esc）の 3 つ。押した瞬間にも判定が要るのは、原子の上から始まるドラッグで
  OrbitControls が回転を始める前に止める必要があるため（capture フェーズで `enabled = false`）。
  先に**モードの無い版で今の挙動をテストで固定**し、viewer をそれ経由にしてから `mode` を足した。
  観測モードでは Shift+クリックも「何もしない」（原子の上でも計測に数えない）。編集モードで
  原子を足す操作なので、別の意味を黙って持たせない。`setMode` はドラッグ中なら打ち切る。
- **P8-3 viewer**:
  - ラベルは `CSS2DRenderer`（DOM を canvas に重ねる層 `.viewer-labels`、`pointer-events: none`。
    子の要素も継承するので、ラベルの上のクリックは下の原子に届く）。`#resize` で canvas と同じ
    CSS ピクセルの大きさにする。**進捗カードに `z-index: 2`、ラベル層に `1`** を付けた: React は
    カードを canvas・ラベル層の前にも後にも挿入しうるので、DOM の順番には頼れない。
  - **破線は `Line` ではなく短い円柱の列**（`dashes.ts` の `dashLayout` が並びを決め、テストつき）。
    WebGL の線は 1 デバイスピクセル固定で、Retina では 0.5 CSS ピクセルになりプロジェクタでは
    見えない。`Line2`（太線）は `setPositions` のたびに属性を作り直す。three の `WebGLAttributes` は
    geometry を `dispose()` したときに**その時点で持っている**属性のバッファしか `deleteBuffer`
    しない（r186 のソースで確認）ので、毎フレーム動かすと置き換えた分が GPU に漏れる。さらに、計測する原子はたいてい結合して
    いるので、結合の軸上に引いた線は結合の円柱に隠れる。円柱の半径を結合の 1.25 倍にして、
    結合の上では縞として見えるようにした。
  - 計測の色は琥珀色 `0xffb84d`（編集の選択の青、等値面の青・赤と区別する）。計測中の原子の
    輪は選択の輪（1.45 倍）と別の大きさにして、両方かかった原子で透明な球が重ならないようにした。
  - **輪と破線の大きさはユーザーの指摘で小さくした**（2026-09-20）: 最初は輪 1.7 倍・破線の半径
    0.11 Å（結合の 1.25 倍）で、電子雲と重なって画面がごちゃつくと言われた。輪 1.2 倍・破線の半径
    0.045 Å（結合の半分）にし、**破線は深度テストを切って手前に描く**（結合より細いと結合の円柱に
    隠れるため。`renderOrder = 2` で等値面より後）。破線は原子の中心から中心まで引く: 結合した
    2 原子の球の隙間は 0.1 Å ほどしかなく、そこに破線を収めると点が 1 つも見えない。
  - 角度のラベルは頂点から角の二等分線の向きに、頂点の輪の外まで出す（`measurementAnchor`）。
    距離は中点、二面角は中央の結合の中点。「結合の長さをすべて表示」は数字だけ（単位はパネル側に
    書く。ベンゼンで 12 個並ぶため）で、計測中の 2 原子の組と同じ結合のラベルは出さない（重なる）。
  - ラベルの文字は変わったときだけ書き換える（アニメーション中は毎フレーム呼ばれる）。
  - **パネルの「今の値」は viewer から受け取る**（`LiveMeasurement` + `useSyncExternalStore`）。
    アニメーション中に画面に描かれている位置は補間されたフレームで React には届かないので、
    App の `atoms` から計算するとラベルと食い違う。表示の桁が変わったときだけ購読者に知らせる。
- **P8-4 App**:
  - **自動切り替え**: 計算の開始時に `restoreModeRef` に今のモードを覚えて観測モードへ。`solved` で
    終われば忘れる（観測のまま）。発散・エラー・中止なら覚えたモードに戻す。**パネルの切り替えを
    ユーザーが押したら覚えたものを捨てる**ので、計算中に自分で選んだモードは終わっても変わらない。
    プリセットを押して計算が中止されたときも「中止」なので戻る。
  - **`relaxedFrom` は緩和の開始時に入れる**（終わってからではない）。アニメーション中から
    「前 → 今」の今が動くのを見せるため。消すのは: 編集（`invalidateResult`）・緩和の発散/エラー・
    緩和の中止。一点計算の中止では消さない（`relaxingRef` で区別。直前の緩和の前後はまだ正しい）。
  - 計測の原子番号列は、原子の並びが変わる操作（追加・削除・全消去・プリセット）で空にし、
    ドラッグ・緩和では残す。viewer への `setMeasured` の effect を `setMolecule` の effect より
    **前に**置いた: 削除で両方が同じ描画で変わるとき、古い番号を新しい原子に当てる瞬間を作らない。
  - 観測モードに入ると編集の選択（青い輪）を外す。Delete が効かないモードで選択だけ残ると紛らわしい。
  - パネルでモードごとに入れ替えるのは「配置する元素」「編集」⇔「観測」だけ。**プリセットは両方の
    モードに残した**（明示的なボタンで、誤クリックで押すものではない。講義で分子を切り替えるのに使う）。
    「全体表示」は「編集」の節にあったので「観測」の節にも置いた。
  - 文言は `components/observe.ts`（テストつき）、節は `ObservePanel.tsx`。「前 → 今」の説明は
    「左が「安定な形にする」を押したときの値、右が今の値です」。二面角が決まらないときは理由を出す。

### 基底と汎関数が構造に与える差（2026-09-20 実測）

きっかけ: P8 で数値が見えるようになり、ユーザーが水の値を教科書と比べた
（このアプリ: r(OH) = 1.031 Å・∠HOH = 96.7°、教科書: 0.957 Å・104.5°）。

**まずエンジンの正しさを切り分けた。** PySCF を同じモデル（LDA(Slater+VWN5) / STO-3G）で、
対称性で決まる 2 変数（r, θ）のエネルギーを直接最小化して比べた（geomeTRIC が入っていないため。
グリッドは PySCF の level 3）:

| | このアプリ（wasm） | PySCF（同じモデル） |
| --- | --- | --- |
| H₂O | 1.0308 Å / 96.74° / −74.743110 Ha | 1.0308 Å / 96.74° / −74.743109 Ha |
| CH₄ | 1.0970 Å | 1.0970 Å |

**一致した。ずれはバグではなくモデル（基底）のもの。** 同じ最小化を基底・汎関数を変えて回した
（実験構造の列はアプリのプリセットの値＝同じ `measure.ts` で測ったもの）:

| モデル | H₂O r(OH) / ∠HOH | NH₃ r(NH) / ∠HNH | CH₄ r(CH) |
| --- | --- | --- | --- |
| LDA/STO-3G（現在） | 1.0308 Å / 96.74° | 1.0649 Å / 100.72° | 1.0970 Å |
| HF/STO-3G | 0.9894 / 100.03 | 1.0325 / 104.16 | 1.0830 |
| LDA/3-21G | 1.0051 / 103.68 | 1.0233 / 113.55 | 1.1023 |
| LDA/6-31G | 0.9845 / 108.53 | 1.0084 / **120.00（平面！）** | 1.1016 |
| **LDA/6-31G\*** | **0.9762 / 103.65** | **1.0269 / 105.99** | **1.1013** |
| PBE/6-31G\* | 0.9768 / 102.78 | 1.0277 / 104.91 | 1.1003 |
| B3LYP/6-31G\* | 0.9687 / 103.65 | 1.0194 / 105.76 | 1.0933 |
| LDA/def2-TZVP | 0.9714 / 105.26 | 1.0221 / 107.57 | 1.0979 |
| プリセット（実験構造） | 0.9578 / 104.47 | 1.0160 / 106.12 | 1.0870 |

読み取れること:

- **角度のずれはほぼ全部が基底（STO-3G が最小基底であること）。** 6-31G\* にすると水の角度は
  7.8° ずれ → 0.8° ずれ、アンモニアは 5.4° → 0.1° になる。LDA を大きな基底（def2-TZVP）で回すと
  実験に近い（水 105.3°）ので、**汎関数（LDA）は角度の主因ではない**。
- **分極関数（d）が要る。** 6-31G（d 無し）は水で 108.5°、アンモニアでは平面（120°）になる。
  分極無しの split-valence は最小基底と逆向きに大きく外す。P9-1 で「平面の NH₃」を試す予定が
  あるが、**現在の基底では平面 NH₃ は最小値ではない**（STO-3G でも 100.7° のピラミッド）一方、
  6-31G だと本当に平面が最小になる、という基底依存があることに注意。
- **結合長には汎関数の分も残る。** CH₄ は基底を上げても LDA では 1.100 Å 前後で、実験（1.087）より
  長い。B3LYP/6-31G\* で 1.093。LDA が結合を長くする分（+0.01〜0.015 Å）は基底では消えない。
- 3-21G は水の角度だけたまたま良い（103.7°）が、アンモニアで 113.6° と大きく外すので、
  「安い代わりに少し悪い」ではなく**当てにならない**。

**差し替えの費用（PySCF の比、grid level 3、3 回の最小値）。** libcint は我々の積分より遥かに
速く、PySCF の内訳は我々と違うので**比だけの目安**:

| | STO-3G | 6-31G\* | |
| --- | --- | --- | --- |
| H₂O | 7 関数 / 0.25 秒 | 19 関数 / 0.25 秒 | 関数 ×2.7、時間 ×1.0 |
| CH₄ | 9 / 0.51 | 23 / 0.61 | ×2.6、×1.2 |
| ベンゼン | 36 / 7.66 | 102 / 20.19 | ×2.8、×2.6 |

我々のエンジンでの効き方は違うはずで、**要るのは差し替えたあとの実測**。効きそうな所:
ERI は 8 重対称で全部持つ（`EriTensor`）ので、ベンゼンは 222,111 個（1.8 MB）→ 13,802,631 個
（**110 MB**）になり、最適化中は新旧 2 つの `System` が生きる。力（ERI 微分）は P7 の実測で
ベンゼン 1 歩あたり約 1 秒を占めていて、四重項の数が 62 倍になるのでここが一番伸びる。
水・アンモニア・メタンは数秒に収まるはず。

**判断（2026-09-20、ユーザー）: このバージョンは STO-3G のまま。** 差し替えは v2 の路線（講義で
使うための UI）と別なので次のバージョンで検討する。記録を実際に貯める予定がまだないので、
「基底を変えると記録が比べられなくなる」という P9 より前にやる理由も当てはまらない。
次バージョンのタスク案は plan-v2.md「基底の差し替え」。

**実装の下地はある**: `basis/mod.rs` は一般の l の Cartesian ガウス（`cartesian_powers`、
libcint と同じ並び）、SAD は実行時に原子を解く（基底を変えてもデータ不要）、
`tests/data/integrals_h2o_631gs.json` が「将来の 6-31G\* 切り替え」のために l=2 の積分を
すでに検証している。残るのは基底テーブルの生成（`gen_reference.py` の `write_sto3g` と同じ形）、
参照値の作り直し、性能とメモリの実測、P9 の `ENGINE_MODEL`。

### P9 の実測（対称性と揺らし、2026-09-20）

すべて Node（コミット済みの `.wasm`）。このマシンは同じバイナリでも ±30% ぶれるので、
歩数のほうが時間より当てになる。

**クリックだけで作った平面の分子は、平面のまま「収束」する。** これが P9-1 の出発点で、
まず現状を確かめたもの:

| 出発構造 | 結果 | エネルギー |
| --- | --- | --- |
| 平面 CH₄（正方形、r = 1.1 Å） | converged · 5 歩 · 面外 0.000000 Å | −39.29933379 Ha |
| 平面 CH₄（角度も長さも崩した「クリックらしい」版） | converged · 13 歩 · 面外 0.000000 Å | −39.29933308 |
| 正四面体 CH₄ | converged · 3 歩 | **−39.61713241** |
| 平面 NH₃（D3h、r = 1.05 Å） | converged · 4 歩 · 面外 0.000000 Å | −55.28155886 |
| ピラミッド NH₃ | converged · 7 歩 | **−55.29630150** |

差は CH₄ で 0.3178 Ha = **834 kJ/mol**、NH₃ で 0.0147 Ha = **38.7 kJ/mol**（反転障壁）。
半径も角度もばらばらの「クリックらしい」版でも面外は 0.000000 Å のままで、丸めではない:
平面に対する勾配の面外成分が厳密に 0 だから、最適化は平面から出られない。

**揺らしの振幅**（平面 NH₃ を seed を変えて揺らし、ピラミッドに落ちたか）:

| 振幅 | 落ちた回数 |
| --- | --- |
| 0.005 Å | 0/3 |
| 0.01 Å | 2/3 |
| 0.02 Å | 2/3 |
| **0.05 Å** | **9/9** |

小さい振幅で平面に戻るのは、面外にずれた量が小さいと面外の力が収束判定（最大力
4.5e-4 Ha/Bohr、エネルギー変化 1e-6 Ha）を下回り、**平面に戻ったところで「落ち着いた」と
判定される**ため。0.05 Å（結合の約 5%）を採用した。平面 CH₄ でも 0.05 は 2/2 で四面体に落ちた。

**同じ谷のばらつき**（落ち着いた構造をさらに揺らして落ち着き直させ、エネルギーの幅を見た）:

| 分子 | 回数 | 幅 |
| --- | --- | --- |
| H₂O | 5 | 5.6e-7 Ha = 0.0015 kJ/mol |
| NH₃（ピラミッド） | 9 | 1.3e-6 Ha = 0.0035 kJ/mol |
| CH₄（四面体から） | 5 | 2.5e-6 Ha = 0.0065 kJ/mol |
| CH₄（平面から落ちた 5 回） | 5 | 1.2e-5 Ha = **0.030 kJ/mol** |

同じ谷に落ちても最後の歩数が違うぶんだけエネルギーが違い、その幅は**最大 0.03 kJ/mol**。
P9-3 の「同じ谷」の閾値はこの 30 倍の **1 kJ/mol** にする（エタンの回転障壁 ~12 kJ/mol、
NH₃ の反転障壁 39 kJ/mol よりはるかに小さく、numerical なばらつきよりははるかに大きい）。

**揺らしの費用。** 落ち着いている構造を揺らすと、戻るのに歩数が要る:

| | 揺らさない | 揺らす（0.05 Å） |
| --- | --- | --- |
| H₂O をもう一度緩和 | 0 歩 · 0.5 秒 | 3〜6 歩 · 1.1〜2.7 秒 |
| CH₄ をもう一度緩和 | 0 歩 · 1.8 秒 | 7〜9 歩 · 4.8〜5.6 秒 |
| ベンゼン（プリセット） | 3 歩 · 24.5 秒 | 14〜23 歩 · 71〜125 秒 |

**面内を動かさない「面の法線方向だけ」の揺らしも試したが、歩数は変わらない**
（ベンゼン 14〜15 歩 · 65〜72 秒、平面 NH₃ の脱出は 0.05 Å で 6/6、0.02 Å でも 6/6 だが
2 回は 60 歩以上かかった）。費用は揺らす向きの問題ではなく、**対称性を失った構造を
収束判定まで持っていく費用そのもの**（BFGS が 3N 個の座標すべてを動かすことになる）。
だから「常に揺らす」のではなく、**揺らす対象を絞る**ことにした（下の実装メモ）。

**ブラウザでの確認**（Claude の Browser ペイン、非表示で間引かれた状態。dev サーバ）:
ベンゼンのプリセットを押すと 3 歩 · 21.1 秒（プリセットなので揺らさない）。**続けてもう一度**
押すと、1 回目の緩和で `presetId` が外れて「手で作った扱い」になるので揺らし、
19 歩 · 131 秒 · −227.264326 Ha（揺らさない場合と 3e-6 Ha ＝ 0.008 kJ/mol 差）。
CH₄ のプリセットは 3 歩 · 8.2 秒、もう一度押すと平面でないので揺らさず
「すでに安定な形でした」· 1.6 秒。App の 2 つの条件が両方効いていることを、この 4 つで確かめた。

**揺らした平面分子は、緩和後も π 判定に十分平らに戻る。** 揺らしたベンゼンの最終構造の
面外は 8.5e-3 Å と 1.8e-3 Å（Node）で、エンジンが分子平面とみなす範囲（`PLANARITY_TOLERANCE`
= 0.06 Bohr = 0.032 Å、`crates/dft-core/src/bonding.rs`）の内側。上のブラウザの 19 歩の
ベンゼンでも「結合に寄与する電子」は π（「平らな分子なので、面から上下にはみ出している
電子だけを表示しています」）のままだった。

### P9 の実装メモ

- **P9-1 揺らし（`web/src/records/perturb.ts`）**
  - **揺らすのは「平らで、かつ手で作った・編集した」構造だけ**（App の `relax()` で
    `presetId === null && isFlat(xyz)`）。理由は上の実測: 揺らしの費用はベンゼンで
    3 歩 → 15 歩（25 秒 → 70 秒）と大きく、しかも**揺らして得があるのは、クリックが
    勝手に作る対称性＝平面に乗った構造だけ**。プリセットや（P9-6 以降）記録から開いた構造は
    カメラ平面から来たものではなく、その対称性は分子自身のもの（ベンゼンは本当に平面）なので
    そのまま送る。計画（plan-v2.md）の当初案は「例外を作らず常に揺らす」だったが、
    実測を見てこの 2 条件に絞った。
  - **平面性の判定（`isFlat`）**: 4 原子未満は常に平面なので `false`（エンジンの
    `MIN_ATOMS_FOR_A_PLANE` と同じ理由）。一直線の並びも `false`（直線を含む平面は無数にあり、
    そのどれも最適化が閉じ込められる対称性ではない）。いちばん離れた 2 原子と、その直線から
    いちばん離れた 1 原子で平面を作り、**それを全原子への最小二乗の平面に直してから**
    すべての原子が `FLATNESS_TOLERANCE`（0.03 Å）以内かを見る。3 点だけの平面では、
    ほぼ平らな構造（1 原子だけ 0.027 Å 浮いた 6 員環）でその原子が「いちばん離れた 1 原子」に
    選ばれて平面が傾き、他の原子が許容の外に出た（最初の実装でテストが落ちた）。
    最小二乗の法線は固有値分解を書かずに `trace(M)·I − M` の累乗法で出す（共分散 M の
    最小固有ベクトル ＝ こちらの最大固有ベクトル。平らな構造では 1 回ごとに誤差が半分になり、
    出発点の 3 点平面がすでに近い）。
  - **許容は 0.03 Å と広め**にした。クリックが作る平面は厳密（1e-15）なので判定だけなら
    どんな許容でもよいが、**ほぼ平らな構造**（カメラをわずかに回しながら置いた、緩和で
    平面近くに戻った）では面外の力が収束判定を下回って止まりうるので、そこも拾う。
  - **振幅 0.05 Å、向きは球面上に一様**（高さを一様に引く。極角を一様に引くと両極に偏る）。
    全原子が同じ距離だけ動き、向きだけが乱数。seed つき（`mulberry32`）にしてあるのは
    テストのためで、App は押すたびに `randomSeed()` を渡す（同じ鞍点に何度も落ちないように）。
  - **`engine.test.ts` に「平面の NH₃」を足した**: 揺らさずに緩和すると面外 < 1e-9 Å のまま
    converged、`PERTURB_AMPLITUDE` で揺らすと面外 > 0.3 Å になり 0.01 Ha 以上下がる。
    コミット済みの `.wasm` を実際に呼ぶので、2 分のタイムアウトを付けてある。
  - **「すでに安定な形でした」は残した**。揺らさない構造（プリセット・平面でない構造）では
    今までどおり 0 歩で出る。手で作った平面構造をもう一度押すと数歩動いて戻るが、
    それは「揺らして確かめた」結果なので文言はそのままでよい。
- **P9-2 単位（`web/src/records/units.json` / `units.ts`）**
  - `gen_reference.py` に `write_units()` を足した。**PySCF は要らず `scipy.constants` だけ**なので
    `main()` を回さずに関数だけ呼べる（`.venv/bin/python -c "... g.write_units()"`、数秒）。
    Hartree のエネルギーと Avogadro をそのまま書き出し、積も入れる（出所が追える）。
  - web 側は `units.ts` が JSON を読んで `HARTREE_TO_KJ_PER_MOL` と `kilojoulesPerMole()` を出す。
    JSON を import するために `web/tsconfig.app.json` に `resolveJsonModule` を足した。
  - **テストは値を書かない**（書いたら生成物にした意味がない）。出所の文字列と桁
    （1e3〜1e4 kJ/mol）、符号が保たれること、NH₃ の反転障壁が 30〜50 kJ/mol に入ることだけ見る。
- **P9-3 記録のモデル（`records/record.ts` / `log.ts` / `file.ts`）**
  - **比較キーは `model | charge | formula`**。電荷が入るのは、中性で解けないときに `driver` が
    ±1 を試すため（電子の数が違うものは差が取れない）。**画面には出さない**（F4）。
    `ENGINE_MODEL = 'sto-3g/lda-vwn5/fine'` は TS の定数で、基底・汎関数・最適化グリッドを
    変えたら書き換える（CLAUDE.md の規約に足した）。
  - **谷はリーダー法でまとめる**（エネルギー順に並べ、*その谷の最も深い記録*から
    1 kJ/mol を超えたら新しい谷）。「1 つ前の記録と比べる」にすると、閾値の 0.9 倍ずつ離れた
    3 件が 1 つの谷に繋がってしまう（テストに入れてある）。
  - **時間切れ・回数上限の記録は順位にも谷にも入れない**が、一覧には残す。テストでは
    「収束した記録より低いエネルギーの途中記録」を入れて、それが谷の底にならないことを見る。
  - **ファイルは 1 件でも駄目なら全部拒否**し、理由（`unreadable` / `format` / `version` /
    `element` / `shape` + 何件目か）を返す。半分だけ取り込むと、教室で空の行や解けない分子が
    出てくる。読み込みは `id` でマージし、**すでにある記録は上書きしない**（名前を変えている
    かもしれない）。同じファイルを 2 回読んでも増えない。
  - **収束していない計算・`reason: 'scf'` の記録は拒否する**（F5。そういう記録はこちらでは
    作られないので、ファイルから入ってくることもあってはならない）。
- **P9-4 保存（`records/store.ts`）**
  - 口（`RecordStore`）・IndexedDB 実装・メモリ実装の 3 つ。テストはメモリ実装に対して書く
    （Node に IndexedDB は無く、偽物を作るとその偽物を試すことになる）。
  - **開けないときは失敗ではなく状態**: プライベートウィンドウなどでは `indexedDB.open` が
    エラーを返す**か、何も返さない**。後者があるので 3 秒で打ち切ってメモリ実装に落とし、
    パネルに「このブラウザには残りません」を出す。
  - `putAll` は 1 つのトランザクション（ファイル読み込みが途中まで入ることがない）。
- **P9-5〜P9-7 パネルと App**
  - **記録は「安定な形にする」の完了時に自動で作る**。軌跡は `onStep` で集める（`FramePlayer` に
    渡す前に `Array.from` でコピー。プレイヤーは渡されたフレームを保持する）。`built` は
    揺らす前の構造なので、記録を開いたときの「前 → 後」が緩和直後と同じ値になる。
  - **記録を開いたら、数値は記録のもの**（最適化の Fine グリッドで解いた値）。等値面には密度が
    要るが密度は記録に入っていない（グリッドは MB 単位）ので、**最終構造で一点計算をやり直し、
    密度だけ**使う。**ここで収束しなくても発散演出は出さない**（記録の数値は正しいままなので、
    黙って等値面を出さないだけ）。
  - **「緩和を再生」は開いている記録だけ**に出す。`setPositions` は今の原子の元素をそのまま使い
    原子数の違うフレームを捨てるので、流す前に `viewer.setMolecule()` で記録の分子にする。
    再生が終わると `animation === null` の effect が `atoms`（＝記録の最終構造）に戻す。
  - **グループの並べ替えは Hill 式だけで**行う（今の分子の組を上に）。比較キーには電荷が入るが、
    画面に出ている分子の電荷は計算するまで分からないため。
  - **ダウンロードはリンクを DOM に入れてから押し、`revokeObjectURL` を 60 秒遅らせる**
    （Firefox は DOM に無いリンクの `click()` を無視し、すぐ revoke するとダウンロードが消える）。
  - **パネルの折りたたみは入れなかった**。代わりに一覧だけ `max-height: 34vh` で区切ってある
    （記録が増えても「電子密度」や数値の節が下に押し出されない）。

### 異性体のエネルギー順序も最小基底で逆になる（C₃H₆、2026-09-20 実測）

**きっかけ**: P9 の記録でユーザーがシクロプロパンとプロペンを作って比べたところ、
**アプリはシクロプロパンのほうが 19.7 kJ/mol 低いと出した**（書き出したファイルは
`docs/C₃H₆-記録-20260920-1859.json`。シクロプロパンは C–C 1.518 Å の正三角形で各 C に H 2 個、
プロペンは C=C 1.336 Å / C–C 1.512 Å）。**実験は逆**で、NIST WebBook の ΔfH°(気相) は
プロペン 20.41 kJ/mol（Furuyama, Golden et al. 1969 ほか）、シクロプロパン 53.30 ± 0.59 kJ/mol
（Knowlton and Rossini 1949）＝ **プロペンが 32.9 kJ/mol 低い**。

**まずエンジンの正しさを切り分けた。** アプリが緩和した 2 つの構造をそのまま PySCF に渡して
一点計算した（`grids.level = 5`。各モデルで構造最適化し直してはいない ＝ venv に geomeTRIC が
無いため。幾何緩和の効きは数 kJ/mol で、下の符号反転を覆す大きさではない）:

| モデル | シクロプロパン | プロペン | プロペン − シクロプロパン |
| --- | --- | --- | --- |
| **このアプリ（wasm）** | −115.347225 | −115.339720 | **+19.7 kJ/mol** |
| LDA/STO-3G（PySCF、同じモデル） | −115.347202 | −115.339721 | **+19.6** |
| HF/STO-3G | −115.664429 | −115.657690 | +17.7 |
| LDA/6-31G | −116.732159 | −116.740682 | −22.4 |
| LDA/6-31G\* | −116.756759 | −116.758506 | −4.6 |
| PBE/6-31G\* | −117.719549 | −117.726276 | −17.7 |
| HF/6-31G\* | −117.055904 | −117.068734 | −33.7 |
| **B3LYP/6-31G\*** | −117.892671 | −117.904797 | **−31.8** |
| LDA/def2-TZVP | −116.813118 | −116.816571 | −9.1 |
| PBE/def2-TZVP | −117.768052 | −117.776550 | −22.3 |
| B3LYP/def2-TZVP | −117.942382 | −117.956828 | −37.9 |
| 実験（NIST、ΔfH の差） | | | **−32.9** |

読み取れること:

- **エンジンは正しい**（同じモデルの PySCF と 0.1 kJ/mol 一致。絶対値の差 2e-5 Ha はグリッド）。
  水の角度のときと同じで、ずれはモデルのもの。
- **符号を変えているのは基底**。STO-3G では汎関数を HF に変えても +17.7 kJ/mol で逆のまま。
  **最小基底 → split-valence（6-31G）にした時点で符号が正しくなる**（LDA で +19.6 → −22.4）。
  価電子の動径の自由度が 1 つしか無いと、環の曲がった結合と二重結合を同じ精度では表せず、
  最小基底は環のほうを不当に得させる。d（分極関数）はそこから大きさを動かすが
  （LDA で −22.4 → −4.6）、符号を決めているのは split-valence のほう。
- **ただし今回は汎関数も効く。** 6-31G\* を固定して汎関数だけ変えると
  **LDA −4.6 → PBE −17.7 → B3LYP −31.8 → HF −33.7**（実験 −32.9）と一直線に良くなる。
  **幾何（角度・結合長）は基底を上げれば LDA でも合うが、異性体どうしのエネルギー差は
  汎関数も上げないと合わず、しかも GGA（PBE）では半分までしか届かない。**
  実験に届くのは厳密交換を混ぜた B3LYP で、それは**エンジンに K 行列（交換積分）を足す**という
  別の実装仕事になる（今のエンジンは Coulomb + LDA の XC だけ）。基底をさらに大きくしても
  LDA は −9.1、PBE は −22.3（どちらも def2-TZVP）で頭打ちなので、**これは基底の不足ではなく
  汎関数そのものの限界**。
- 途中の行に惑わされないこと: **LDA/6-31G（d 無し）の −22.4 は実験に近いが偶然**で、
  d を足した 6-31G\* では −4.6 に戻る。水の角度で 3-21G がたまたま良かったのと同じ型の偶然。
- 実験値は ΔfH（ZPE と熱補正込み）、計算は電子エネルギーの差。両者を 1 kJ/mol の桁で比べる
  ものではないが、符号と「30 kJ/mol 程度」は動かない。

**他の組でも確かめた（P9-9、2026-09-20）。** C₃H₆ だけの話ではなかった。アプリで作って緩和した
構造をそのまま使った比較:

| 組 | 比べる向き | **アプリ（LDA/STO-3G）** | LDA/6-31G\* | PBE/6-31G\* | B3LYP/6-31G\* | 実験 |
| --- | --- | --- | --- | --- | --- | --- |
| 異性体 C₃H₆ | プロペン − シクロプロパン | **+19.6（逆）** | −4.6 | −17.7 | −31.8 | **−32.9** |
| 異性体 C₂H₆O | ジメチルエーテル − エタノール | **−28.2（逆）** | +9.3 | +7.8 | +5.2 | **+49.9** |
| 配座 C₂H₆ | 重なり形 − ねじれ形 | **+13.5（合う）** | +14.0 | — | +14.3 | **約 12** |

- **異性体は 2 組とも符号が逆**。C₂H₆O はアプリで作った構造（エタノール 16 歩、ジメチルエーテル
  58 歩、どちらも収束。C–C 1.551 / C–O 1.456 / O–H 1.032 Å）で、実験値は NIST WebBook の
  ΔfH°(気相): エタノール −234 ± 2 kJ/mol（9 値の平均）、ジメチルエーテル −184.1 ± 0.50
  （Pilcher, Pell et al. 1964）＝ **エタノールが 49.9 kJ/mol 低い**。
- **配座（つながり方が同じで、ねじれだけ違う）はアプリのモデルでも合う。** エタンの回転障壁は
  13.5 kJ/mol（剛体回転。同じ構造で 6-31G\* にしても 14.0、B3LYP でも 14.3）で、教科書値の
  約 12 kJ/mol と同程度。**ここが P9 の記録の使いどころ。**
- **C₂H₆O の「大きさ」は、この表からは読めない**（符号だけが読める）。B3LYP/6-31G\* でも +5.2 で
  実験の +49.9 に遠いのは、**構造がアプリの（LDA/STO-3G の）ままだから**と見ている:
  エタノールの O–H は 0.06 Å 長く、O–H は固い結合なので、良いモデルで測るとそれだけで
  20 kJ/mol 級の不利になる（½kx² の見積もり）。ジメチルエーテルに O–H は無い。C₃H₆ の組には
  こういう固い結合の差が無く、そちらは固定構造でも実験に合った。
  **各モデルで構造最適化し直した比較は v3 の実測でやる**（venv に geomeTRIC を入れる）。

**講義での扱い（v2、STO-3G のまま）**: **異性体どうしのエネルギーの比較には使えない**
（2 組とも順序が逆）。**同じつながり方の形（配座・角度・結合長）の比較は使える**
（エタンの障壁は合う）。この組はむしろ「近似のモデルを変えると答えがひっくり返る」例として
使える。**v3 では基底と汎関数を一緒に見直す**（plan-v2.md「次のバージョン（v3）で検討すること」）。

**画面にも 1 行出すことにした**（2026-09-20 ユーザー判断）。記録の節の説明文に
`ISOMER_CAVEAT`（`components/records.ts`）を足した: 「くらべられるのは、同じつながり方の分子の
形どうしです。つながり方が違う分子（異性体）どうしのどちらが安定かは、この計算では当てに
なりません。」 基底も汎関数も出さないので F4 に触れない（テストで語を禁止している）。
黙っていると、教室で逆の結論がそのまま出てしまうため。

### P10-1 の実測（並列探索、2026-09-20）

すべて Node（`worker_threads` + `--target nodejs` の release ビルド）。**開発機は 2 物理コア /
4 論理（i5-5287U、`hardwareConcurrency` は 4）**で、講義で使う PC（i5-1235U、P 2 + E 8、
12 スレッド）とは別物。ここで決めたのは**形**（どこで頭打ちになるか、何を犠牲にして何が増えるか）で、
**数そのものは講義 PC で確かめる**（P10-6）。この機械は同じバイナリでも ±30% ぶれる（規約の詳細）。

#### 同時に回した本数と処理量

同じ分子の `optimize` を N 本同時に回し、N 本ぶんが終わるまでを測った（2 回の最小値）。

| 分子（Worker が持つ WASM の山） | N=1 | N=2 | N=3 | N=4 | N=5 | N=6 |
| --- | --- | --- | --- | --- | --- | --- |
| CH₄（15 MiB） 1 本の時間 | 3.3 秒 | 5.2 | 7.5 | 11.2 | 12.2 | 14.8 |
| CH₄ 処理量（本/秒） | 0.302 | 0.384 | 0.392 | 0.352 | 0.405 | 0.402 |
| C₂H₆（50 MiB） 1 本の時間 | 15.5 秒 | 34.3 | 43.6 | 53.9 | — | — |
| C₂H₆ 処理量 | 0.065 | 0.058 | 0.069 | 0.074 | — | — |
| ベンゼン（139 MiB） 1 本の時間 | 27.7 秒 | 56.9 | 60.8 | 79.3 | — | — |
| ベンゼン 処理量 | 0.036 | 0.035 | 0.049 | 0.050 | — | — |

**2 物理コアでは、どの分子でも処理量は 1.3〜1.4 倍で頭打ち**になり、それ以上の Worker は
1 本あたりの時間を比例して延ばすだけだった（ベンゼン N=4 は 1 本 79 秒 ＝ 単独の 2.9 倍）。
N=2 だけ利得が出ない分子（C₂H₆・ベンゼン）があるのは、2 本が同じ物理コアの 2 つの論理
プロセッサに載ることがあるためと考えている（どこに載るかは OS が決め、こちらからは指定できない）。
一連の計測の最後にベンゼン N=1 を測り直すと 27.7 → 34.4 秒だったので、上の表の大きい N は
不利側に出ている。それでも**「頭打ちの後は 1 本あたりが比例して遅くなる」形は変わらない**。

#### 前面の Worker の応答（プールの大きさを決めたのはこれ）

前面の Worker で H₂O の一点計算を繰り返しながら、裏で N 本のベンゼン最適化を回し続けた
（9 回の中央値）:

| 裏で回している候補 | 前面の H₂O 一点 | 何もしないときとの比 |
| --- | --- | --- |
| 0 本 | 380 ms | ×1.0 |
| 1 本 | 464 ms | ×1.2 |
| 2 本 | 932 ms | ×2.5 |
| 3 本 | 1420 ms | ×3.7 |

**境目は「物理コア − 前面の 1 本」**で、それを超えると前面の応答が候補の本数にほぼ比例して
悪くなる。処理量は 1.4 倍までしか増えないのに前面は 3.7 倍遅くなるので、**取りにいく価値のある
同時実行数はそこまで**。

#### Worker 1 つの値段

- **起動**: Node の `worker_threads` で 267〜463 ms。そのうち**エンジン（`.wasm` のコンパイル +
  インスタンス化 + `start`）は 8〜25 ms しかない**。→ **P10-5（モジュールを 1 回だけコンパイルして
  配る）は、少なくとも Node では効かない**。ブラウザは `.wasm` の取得とコンパイルの割合が違うので、
  やるなら先にブラウザで起動時間を測ること。
- **メモリ**: 読み込み直後 1.1 MiB → H₂O 11.9 → CH₄ 15〜20 → C₂H₆ 50 → **ベンゼン 113〜139 MiB**。
  **WASM の線形メモリは縮まないので、一度ベンゼンを回した Worker は終了するまでその山を持ち続ける**
  （続けて H₂O・CH₄ を回しても 113.3 MiB のまま）。候補はどれも同じ分子なので山も同じ＝
  **バッチの間は使い回してよく、バッチが終わったら Worker ごと捨てる**。ベンゼンで候補 3 本なら
  約 420 MiB（＋前面の 139 MiB）。

#### JS から候補を打ち切れるか

**打ち切れる。`on_step` のコールバックから例外を投げると、`optimize` はそこで止まり
`reason: 'interrupted'` の普通の結果を返す**（`dft-wasm` の `on_step.call1(...).is_err()`）。
Rust も `.wasm` も変えずに済み、`terminate()` と違って**そこまでの構造が返ってくる**:

```
stopped after step 1 (5.2 s): reason=interrupted converged=false steps=1 scfConverged=true
  structure came back: 5 atoms, energy -39.617034 Ha
  the calculation is still usable: 2022 vertices
```

`hasUsableStructure()` が真なので、記録には今までどおり「途中」として入る。`Calculation` は
生きたままなので、そのあと等値面も出せる。

**`crates/dft-wasm/src/lib.rs` の `optimize` の doc は「`on_step` が `false` を返すと止まる」と
書いていたが、実際には JS の戻り値を読んでいない**（`is_err()` だけを見て、そうでなければ
エンジン自身の予算で判断する）。止める手段は例外を投げること。doc をそう直した（コメントだけ
なので `.wasm` は変わらない）。

#### 候補を揺らす振幅

P9 の揺らし（0.05 Å）は**平面の対称性から降りる**ためのもので、探索の候補にそのまま使えるとは
限らない。4 つの出発構造を seed 5 通り（C₂H₆ だけ 3 通り）× 振幅で緩和し、どこに落ちたか・
いくらかかったかを見た（同じ谷の判定は記録と同じ 1 kJ/mol）。

**(a) クリックだけで作った平面の CH₄**（平面のまま「収束」する。正四面体は 834 kJ/mol 下）:

| 振幅 | 正四面体に降りた | 平面のまま | 別の停留点 | 中央値の歩数 |
| --- | --- | --- | --- | --- |
| 揺らさない | 0/1 | 1/1 | — | 5 |
| 0.05 Å | 4/5 | 1/5 | — | 14 |
| 0.10 Å | **5/5** | 0 | — | 15 |
| 0.20 Å | 4/5 | 1/5 | — | 15 |
| 0.30 Å | 3/5 | 1/5 | 1/5（−39.3614 Ha ＝ 正四面体の 671 kJ/mol 上） | 17 |
| 0.50 Å | 4/5 | 0 | 1/5（同じ −39.3614） | 21 |

**(b) 手でクリックしたような、対称性の無い CH₄**（結合 1.24〜1.45 Å、ばらばら）:

| 振幅 | 揺らさない | 0.10 | 0.20 | 0.30 | 0.50 Å |
| --- | --- | --- | --- | --- | --- |
| 落ちた谷 | 正四面体 | **5/5 とも同じ正四面体**（差は 0.01 kJ/mol 以内） | 5/5 | 5/5 | 5/5 |
| 中央値の歩数 | 14 | 13 | 14 | 14 | 15 |

**(c) H₂O₂（ねじれの自由度がある）**と**(d) エタン（ねじれ形 ＝ 対称）**:

| | 揺らさない | 0.10 | 0.20 | 0.30 | 0.50 Å |
| --- | --- | --- | --- | --- | --- |
| H₂O₂ 元の谷 | 1/1 · 7 歩 | 5/5 · 10 歩 | 5/5 · 12 歩 | 5/5 · 12 歩 | 4/5 · 22 歩（1/5 は **263 kJ/mol 上**の別の形） |
| C₂H₆ 元の谷 | 1/1 · 8 歩 | — | 3/3 · 33 歩 | 3/3 · 35 歩 | — |

読み取れること:

- **対称性の無い構造は、いくら揺らしても同じ谷に落ちる。** 0.5 Å（結合のほぼ半分）動かしても
  歩数すら変わらない。**揺らして得があるのは、P9 と同じく対称な（平面の）構造だけ。**
- **平面から降りられるかどうかは、振幅よりも向きで決まる。** 同じ seed が 0.10 では降り、
  0.05 と 0.20 では平面に戻った（その向きがほぼ面内だったため）。だから**「大きく揺らす」より
  「何通りも試す」ほうが効く** — それがプールの役目でもある。
- **0.3 Å を超えると、別の停留点に落ちる候補が出る**（CH₄ で 671 kJ/mol 上、H₂O₂ で 263 kJ/mol 上）。
  力は釣り合っているが、講義で「もう一つの形」として見せたいものではない。振動解析をしない
  以上、谷底と峠は区別できない（plan-v2.md「後回しにしたもの」）。
- **SCF が壊れることは一度も無かった**（最も近い 2 原子が 0.59 Å まで詰まった候補でも収束した）。
  dev-notes「P4 で分かったこと」の「非収束を作るのは難しい」と同じ。だから原子の重なり検査は
  **計算を守るためではなく、ユーザーが作った分子と呼べないものを候補にしないため**のもの。
- **費用は歩数で 1.5〜4 倍**（対称なエタンは 8 歩 → 33 歩。P9 のベンゼン 3 歩 → 14〜23 歩と同じ話）。

#### ここで決めた値（2026-09-20、ユーザー）

- **プールの同時実行数の上限 3**、実際の本数は
  `min(3, max(1, floor(hardwareConcurrency / 2) − 1))`。開発機（4）は 1 本 ＝ 上の実測どおり、
  講義 PC（12）は 5 → 3 に丸まる。3 にしたのは、処理量が頭打ちなのに前面が比例して遅くなること、
  ベンゼンで 3 本 ＝ 約 420 MiB になること、15 W の薄型機で全コアを数分回すと熱で落ちること。
- **JS 側の打ち切りを入れる。1 候補 10 分**（例外方式）。健全な候補は余裕で収まり
  （揺らしたベンゼンが単独 ~130 秒、混雑時でも ~400 秒の見込み）、詰まった候補が枠を
  占め続けるのを防ぐ。エンジンの `OPTIMIZE_BUDGET_SECONDS`（1800 秒）と `max_steps`（100）は
  そのまま。
- **候補を揺らす振幅 0.20 Å**。平面から降り、どのテストでも変な形は出ず、0.3/0.5 より安い。
- **原子の重なり検査は「共有結合半径の和の 0.6 倍」より近い組があれば引き直す**。実測では
  0.59 Å まで詰まっても収束したので、これは計算を守る閾値ではなく「分子と呼べる候補だけを送る」
  ための番人。

### P10 の実装メモ

- **Worker は前面 1 本 + プール**（`web/src/search/pool.ts`）。プールは `DftWorkerClient` を
  そのまま人数分持つ（偽 Worker でテストできる経路がそのまま使える）。
  - **大きさは `poolSize(navigator.hardwareConcurrency)`** ＝
    `min(3, max(1, floor(報告値 / 2) − 1))`。半分にするのは論理プロセッサから物理コアを
    当てる当て推量、1 引くのは前面のぶん。報告しないブラウザは 1。**理由は処理量ではなく
    前面の応答**（P10-1 の実測）。
  - **Worker はバッチの間だけ使い回し、キューが尽きたら捨てる**（`#pump` の最後で
    `#releaseWorkers`）。WASM の線形メモリは縮まないので、ベンゼンを 1 回回した Worker は
    終了するまで 139 MiB を持ち続ける。候補は全部同じ分子なので山は同じ。
  - **候補ごとの中止は、その枠の `client.cancelAll()`**（＝ terminate + 再生成）。
    先に候補を `cancelled` にしてから呼ぶので、そのあと届く reject を「失敗」と取り違えない。
  - **`onChange` は候補の浅いコピーを毎回作る。** 候補は step が届くたびに書き換わるので、
    同じオブジェクトを渡すと React が行を描き直さない。軌跡は共有のままにしてコピーしない。
  - **`dispose()` は通知しない**（App の unmount から呼ばれる。そこでの `setState` は無意味）。
    テストは `pool.candidates` を直接見る。
- **1 候補の予算は `protocol.ts` の `optimize` に足した `budgetMs`。** Worker の step
  コールバックで期限を過ぎていたら**例外を投げる**（`dft.worker.ts`）。エンジンは
  「送る相手がいなくなった」として止まり、`reason: 'interrupted'` ＋ そこまでの構造を返す。
  `terminate()` と違って構造が残るのが肝で、記録には「途中」として入る。
  前面の Worker は `budgetMs` を送らない（止めるのは中止ボタン）。
  **`dft-wasm` の doc が「`on_step` が `false` を返すと止まる」と書いていたのは誤り**で、
  戻り値は読んでいない（実測で確かめてから doc を直した）。
- **候補の生成（`web/src/search/candidates.ts`）**
  - **`SEARCH_AMPLITUDE = 0.2 Å`**（P9 の `PERTURB_AMPLITUDE` 0.05 Å とは別の仕事）。
    根拠は P10-1 の実測。**対称性の無い構造では揺らしても同じ谷に落ちる**ので、
    「今の形を試す」は揺らさずに送る。
  - **重なり検査は共有結合半径の和の 0.6 倍**（`overlaps`）。元素ごとに違う値になるのが要点で、
    H–H は 0.74 Å で結合し C–C は 1.5 Å で結合する。引き直しは 8 回まで。
    **それでも駄目なら、そのまま送る**: 画面にある構造を緩和して出た答えのほうが、
    「候補を作れません」より正直。
  - 記録の `id` に**候補の id をそのまま使う**。探索の行が「自分が作った記録」を引けて、
    相対エネルギーと「開く」がそれだけで書ける。
- **UI（`components/SearchPanel.tsx` / `search.ts`）**
  - 節の名前は「**形をさがす**」。ボタンは「今の形を試す」「ゆらして 3 通り試す」。
    `NUDGED_COUNT` はプールの本数より多くてよい（**効くのは向きを何通り試すか**であって
    振幅ではない）。入りきらない候補は並んで待つ。
  - **相対エネルギーは記録の `relativeText` をそのまま呼ぶ**ので、探索の行と記録の行が
    食い違わない。そのために `records/log.ts` に `entryFor(groups, recordId)` を足した。
  - **非収束の行は「—」だけ**（F5）。数値も「失敗」の語も出さない。開くと、その候補の
    **初期構造**を画面に置いて発散演出を流す（記録は作られないので開く先が無い）。
  - 経過時間の時計は**この節の中で回す**（進捗カードと同じ作り）。プールの `now` も
    `performance.now()` に揃えてある（`Date.now()` と混ぜると経過時間が狂う）。
  - 候補は `atoms`・`FramePlayer`・前面の Worker を**一切触らない**。触るのは「開く」だけで、
    それは記録を開く既存の経路（`openRecord`）に渡す。

### v3-0 の実測: 基底と汎関数を上げると何がどれだけ変わり、いくら掛かるか（2026-09-21）

**目的**: 「計算の精度をユーザーが選べるようにする」ための段を、当て推量ではなく実測で切る。
2026-09-20 の 2 節（「基底と汎関数が構造に与える差」「異性体のエネルギー順序も最小基底で逆に
なる」）は**構造を固定したまま**モデルを変えていたので、**geomeTRIC を venv に入れて、どの
モデルも自分で構造最適化する**ところからやり直した。比べる組も 2 → 5 に増やした
（シス/トランスと分岐アルカンを足した ＝ ユーザーが「高い段が要る」と考えていた用途）。

道具: `.venv`（pyscf 2.14.0・geometric 1.1.1・rdkit 2025.9.2 を追加）。**Cartesian d**
（`mol.cart = True`）でエンジンと関数の数を揃える。最適化はグリッド level 4、最後のエネルギー
だけ level 5。出発構造はプリセット（H₂O・NH₃・CH₄）、アプリの記録（C₃H₆ の 2 つ）、
RDKit + MMFF（C₂H₆O・C₄H₁₀・C₄H₈・C₂H₆）。**B3LYP は libxc の 402**
（`HYB_GGA_XC_B3LYP` ＝ B88 + LYP + VWN_RPA + 厳密交換 20%）で、PySCF 2.14 の `'b3lyp'` が
これ。VWN5 版が要るなら `'b3lyp5'` は別物。
PySCF 側の測定スクリプトは使い捨てで**残していない**（`survey.py` / `cross2.py` /
`ceiling.py` / `polar_h.py` / `analyze.py`）。残したのは
`crates/dft-core/examples/basis_cost.rs`（エンジン自身の値段を測る例）だけ。
実験値の出どころは NIST WebBook（下の表の脚注）。

#### 1. エンジンは 6-31G\* でも正しい（先に確かめた）

`BasisSet::from_shells` が公開されているので、**エンジンを一行も変えずに** 6-31G\* の `System`
を組める（そのための測定専用の例を `crates/dft-core/examples/basis_cost.rs` に置いた。
`System::build` は STO-3G 決め打ちなので、この例だけが `System` を自分で組み立てている）。
水のプリセット構造で一点計算すると:

| 基底 | 関数 | PySCF | このエンジン |
| --- | --- | --- | --- |
| STO-3G | 7 | −74.732059 | −74.732059 |
| 6-31G | 13 | −75.817934 | −75.817934 |
| 6-31G\* | 19 | −75.844389 | −75.844388 |

ベンゼンのプリセット構造でも 6-31G\* で −230.090762（PySCF）に対し **−230.090758**。
**d 関数を含めて一致する。** `integrals` の MD は l に依存しないと書いてあるとおりで、
6-31G\* に上げる仕事は**新しい物理ではなく配線**（基底表の生成と、`System::build` /
`guess::atomic_density` / `opt` が STO-3G を決め打ちしている所）。

#### 2. 幾何: 角度は基底で決まり、結合長は汎関数で決まる

各モデルが自分で最適化した値と、（プリセット ＝ 実験構造に対する誤差）:

| モデル | H₂O r / ∠HOH | NH₃ r / ∠HNH | CH₄ r |
| --- | --- | --- | --- |
| LDA/STO-3G（現状） | 1.0308 (+0.073) / 96.74 (−7.73) | 1.0649 (+0.049) / 100.72 (−5.40) | 1.0970 (+0.010) |
| LDA/6-31G | 0.9844 (+0.027) / 108.53 (+4.06) | 1.0084 (−0.008) / **120.00 (+13.88、平面)** | 1.1016 (+0.015) |
| LDA/6-31G\* | 0.9762 (+0.018) / 103.65 (−0.82) | 1.0269 (+0.011) / 105.99 (−0.13) | 1.1013 (+0.014) |
| LDA/6-31G\*\* | 0.9734 (+0.016) / 103.56 (−0.91) | 1.0259 (+0.010) / 105.79 (−0.33) | 1.1000 (+0.013) |
| PBE/6-31G\* | 0.9768 (+0.019) / 102.78 (−1.69) | 1.0277 (+0.012) / 104.91 (−1.21) | 1.1003 (+0.013) |
| **LDA+20%HF/6-31G\*** | 0.9666 (+0.009) / 104.30 (−0.17) | 1.0182 (+0.002) / 106.55 (+0.43) | 1.0943 (+0.007) |
| LDA+50%HF/6-31G\* | 0.9540 (−0.004) / 105.08 (+0.61) | 1.0063 (−0.010) / 107.17 (+1.05) | 1.0843 (−0.003) |
| B3LYP/6-31G\* | 0.9687 (+0.011) / 103.65 (−0.82) | 1.0194 (+0.003) / 105.76 (−0.36) | 1.0933 (+0.006) |
| HF/6-31G\* | 0.9473 (−0.011) / 105.50 (+1.03) | 1.0025 (−0.014) / 107.18 (+1.06) | 1.0837 (−0.003) |
| 実験（プリセット） | 0.9578 / 104.47 | 1.0160 / 106.12 | 1.0870 |

- **角度のずれはすべて基底**。STO-3G の 5〜8° が 6-31G\* で 1° 以内になる。2026-09-20 の
  固定構造の表と同じ値が出た（あの表は幾何については正しく読めていた）。
- **GGA（PBE）は幾何を直さない**。LDA/6-31G\* とほぼ同じで、水の角度はむしろ少し悪い。
- **結合長は基底では直らない**。LDA は 6-31G\* でも +0.010〜0.015 Å 長く、**CH₄ は
  STO-3G（+0.010）のほうが 6-31G\*（+0.014）より実験に近い**。直すのは厳密交換
  （LDA+20%HF +0.007、B3LYP +0.006）。50% では行き過ぎて HF 側に外す。
- **6-31G\*\*（H にも分極関数）は効かない**（水 0.9762 → 0.9734 で、まだ +0.016）。
  関数はベンゼンで 102 → 120 に増える。**採らない。**

#### 3. エネルギー: 符号は基底、大きさは汎関数、ただし組ごとに事情が違う

各モデルが自分で最適化した構造どうしの差（kJ/mol）:

| 組 | 比べる向き | LDA/STO-3G | LDA/6-31G\* | PBE/6-31G\* | LDA+20%HF | B3LYP/6-31G\* | HF/6-31G\* | 実験 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 異性体 C₃H₆ | プロペン − シクロプロパン | **+19.6（逆）** | −5.4 | −18.7 | −6.8 | **−32.4** | −33.1 | **−32.9** |
| 異性体 C₂H₆O | ジメチルエーテル − エタノール | **−15.1（逆）** | +26.9 | +27.0 | +29.4 | +24.3 | +28.4 | **+49.9** |
| 異性体 C₄H₁₀ | イソブタン − n-ブタン | −4.7 | **−8.1** | −5.9 | −7.5 | −5.5 | — | **−8.5** |
| シス/トランス C₄H₈ | トランス − シス | −2.3 | **−3.4** | −4.9 | −4.1 | −5.6 | — | **−3.1** |
| 配座 C₂H₆ | 重なり形 − ねじれ形 | +12.2 | +12.9 | +12.3 | +12.9 | +12.4 | +13.1 | **約 12** |

実験値: C₃H₆ と C₂H₆O は 2026-09-20 の節と同じ NIST WebBook の ΔfH°(気相)。
C₄H₁₀ は n-ブタン −125.6 ± 0.67 / イソブタン −134.2 ± 0.63（どちらも Pittam and Pilcher,
1972）＝ **−8.6**、同じ Prosen, Maron et al., 1951 の対でも −8.5。
C₄H₈ はシス −7.7 ± 1.3 / トランス −10.8 ± 1.0（どちらも Prosen, Maron et al., 1951）＝ **−3.1**。
**同じ測定の対どうしで引いている**ので、差は絶対値より確か。計算は電子エネルギーの差で
ZPE と熱補正が入っていないため、1 kJ/mol の桁で比べるものではない。

- **現状（LDA/STO-3G）でも符号が合う組がある。** 配座（+12.2）、**シス/トランス（−2.3）**、
  **分岐（−4.7）**。**ユーザーが「高い段が要る」と考えていたシス/トランスは、今でも順序は
  合っている。**
- **符号が逆になるのは「つながり方が大きく違う」2 組だけ**（環 vs 二重結合、エーテル vs
  アルコール）。**どちらも 6-31G\* にした時点で直る。**
- **大きさは組ごとに事情が違う**:
  - **C₃H₆ は汎関数が全部**（LDA −5.4 → PBE −18.7 → B3LYP −32.4、実験 −32.9）。
    **厳密交換を LDA に混ぜるだけでは直らない**（LDA+20%HF で −6.8、50% でも −10.6）。
    効いているのは GGA のほう。HF 単独（−33.1）が当たるのは相関汎関数が無いからで、
    LDA 相関が環を不当に得させているということ。
  - **C₂H₆O はどのモデルでも半分**（B3LYP/6-31G\* で +24.3、実験 +49.9）。基底を上げると
    埋まる: B3LYP/def2-SVP +37.5、**B3LYP/def2-TZVP +41.4**、LDA/def2-TZVP +46.6
    （いずれも B3LYP/6-31G\* の構造での一点）。**6-31G\* 自身の限界**で、汎関数では埋まらない。
    2026-09-20 に「アプリの構造が悪いせい」と見立てたのは**外れ**だった。
  - **C₄H₁₀ と C₄H₈ は LDA/6-31G\* が一番実験に近く、B3LYP はむしろ 3 kJ/mol 悪い。**
    「高いモデルほど良い」とは限らない。ただし**6-31G\* ならどのモデルも符号は間違えない。**

#### 4. 決め手: 高いモデルは「安い構造の上での一点計算」でよい

同じ B3LYP を、(a) 自分で構造最適化した場合、(b) LDA/6-31G\* の構造の上で一点計算した場合、
(c) LDA/STO-3G の構造の上で一点計算した場合:

| 組 | B3LYP//B3LYP | B3LYP//LDA/6-31G\* | B3LYP//LDA/STO-3G | 実験 |
| --- | --- | --- | --- | --- |
| C₃H₆ | −32.4 | −32.3 | −32.6 | −32.9 |
| C₂H₆O | +24.3 | +24.9 | +21.3 | +49.9 |
| C₄H₁₀ | −5.5 | −5.8 | −6.2 | −8.5 |
| C₄H₈ | −5.6 | −6.0 | −6.7 | −3.1 |

**(a) と (b) は 0.6 kJ/mol 以内、(c) でも 3 kJ/mol 以内。つまり高い段に交換や GGA の勾配は
要らない。** これが実装の大きさを決める:

`deriv.rs` の二電子勾配は `DensityPair` で密度をシェルペアの Hermite 係数に畳み込み、
**四重項の積分ブロックを一度も作らない**（「The integral blocks never exist.」）。これは
Coulomb 項 `Σ D_μν D_λσ ∂(μν|λσ)` が bra 側と ket 側に分解できるから成り立つ形で、交換項
`Σ D_μλ D_νσ ∂(μν|λσ)` は密度が bra と ket をまたぐので**同じ形に畳めない**。交換の勾配を
入れるには積分ブロックを実体化する別経路が要り、CLAUDE.md が「崩すな」と書いている前提
そのものを外すことになる（d シェルでは 1 四重項あたり 6⁴ × 12 個）。**一点計算に限れば、
その話が丸ごと消える。**

ただし**「構造の精度には鈍感だが、別の極小に落ちた構造には敏感」**。2026-09-20 にアプリの
構造の上で測った C₂H₆O の B3LYP は +5.2 だったが、今回 PySCF が LDA/STO-3G で最適化した構造の
上では +21.3 になった。モデルも基底も同じでこれだけ動くのは**配座（どの極小に落ちたか）が
違う**ため。**形を見つけるのは、どの段でも形の段の仕事。**

#### 5. 値段（このエンジン自身で測った）

`cargo run --release --example basis_cost`（ネイティブ、2〜3 回の最小値。初期推定は
どの基底でも core Hamiltonian に揃えてあるので、SCF の回数はアプリ（SAD）より多い）。

- **倍率は分子の大きさで変わる**: 水 2 倍、C₃H₆ 4.6 倍、ベンゼン 8.1 倍。ベンゼンの
  「安定な形にする」はブラウザで約 15 秒（P7 の実測）なので、**6-31G\* では 2 分前後**になる。
  水・メタンは 6-31G\* でも数秒のまま。
- **6-31G\* では SCF が主役になり、その半分は保存済み ERI からの J**（ベンゼンで 1 回 0.45 秒
  × 12 回 ＝ 5.4 秒）。STO-3G では J は誤差の内だった（0.006 秒）。
- **K は J と同じ値段**（ベンゼン 0.50 対 0.45）。**厳密交換を混ぜても SCF が 1.5 倍になるだけ**
  で、積分を作り直さない。段 3 を一点計算に限るなら、これが追加コストのすべて。

  1 本がベンゼン STO-3G で 139 MiB だったので、6-31G\* では **250 MiB 前後**になる。
  **WASM の線形メモリは縮まない**ので、探索のプール（同時 3 本）を 6-31G\* で回すと
  1 GiB に近づく。**探索は最小基底に固定するのが前提。**

### V3-1 の実装メモ（エンジンが基底を選べるようにする、2026-09-21）

- **形**: `BasisKind { Sto3g, B631Gs }`、`BasisSet::build(kind, &molecule)`（`sto3g()` はその包み）、
  `System::kind`。引数の順は **分子 → 基底 → グリッド**: `System::build(molecule, kind, quality)` /
  `build_with_grid(molecule, kind, grid)`。wasm は当面 `BasisKind::Sto3g` 固定（段を通すのは V3-3）。
- **`System` から別の `System` を組む箇所は 2 つ**で、どちらも `system.kind` を引き継ぐ: SAD の原子
  （`guess::atomic_density(z, kind)`）と最適化の毎歩（`opt::evaluate`）。取り違えると SAD は原子
  ブロックの大きさが合わず（debug は `debug_assert`、release は添字外）、最適化は前の歩の密度
  （再出発の初期推定）と大きさが合わずに落ちる。最適化のほうは `System::build` を STO-3G 決め打ちに
  戻して、`optimize.rs` の `every_step_keeps_the_basis_it_started_in` が落ちることを確かめた。
- **`superposition_of_atomic_densities` は `(molecule, basis)` ではなく `&System` を取る。** 種類を
  別の引数にすると、分子の基底と食い違う組を渡せてしまう。**チケットの「キャッシュの鍵を
  `(z, kind)` に」は採らなかった**: キャッシュは 1 回の呼び出しの中だけのもので、その間の基底は
  1 つなので `z` で足りる。

  直した値で、表にあるのは公表値。両方を `Shell::new` に通し、規格化した後で比べる（相対 1e-12）。
  O の 1s の係数を 0.1% 変えると落ちることを確かめた。STO-3G の表のテストも同じ関数に寄せた
  （係数の比較が増えただけ）。

  つきのテストが通るだけでは「値が動いていない」とは言えないので、一時的な example を作った。

### P3・P4 の実装メモ

- **Worker は `Calculation` ハンドルを保持している。** `dft-wasm::scf()` は
  `Calculation`（`System` + `ScfResult` + チャンネルごとに遅延生成する ρ グリッド）を返し、
  `summary()` がスカラー値、`isosurface(channel, level)` がメッシュを返す。
  `dft.worker.ts` の `current` がそれを持ち、新しい SCF のたびに古いものを `free()` する
  （WASM のメモリは GC されない）。
  P4 で UKS を足したが、等値面側は変わっていない（`ScfResult::density` は α+β の全密度）。
- **`worker.terminate()` は保持中の `Calculation` も道連れにする。** 中止や編集のあと
  等値面を再生成するには SCF からやり直しになる。UI 側は `hasDensityRef` でそれを追跡
  している。発散アニメーション中に等値面を出したいなら、この前提を見直すこと。
- **等値面リクエストは App 側で合流させている**（`wantedRef` + `meshInFlightRef`）。
  Worker は単一スレッドなので、スライダーのイベントを全部キューに積むと数秒遅れる。
- **非収束でも密度は返る**が、**描かないことにした**。`ScfResult` は `converged: false`
  でも形式上は密度を持つけれど、それは「その分子の密度」ではなく「反復が止まらなかった
  最後の 1 枚」なので、飛び散る原子の隣に電子雲を出すと「計算できた」に見えてしまう。
  発散演出だけを出し、数値も等値面も伏せる。
- **表示チャンネルは 2 つある。** UI は `total` か `bonding` を要求し、`bonding` に対して
  **どう答えるかはエンジンが決める**（`bonding::bonding_channel`）。平面分子なら π、
  それ以外は差密度（ρ_分子 − ρ_孤立原子の重ね合わせ）。返ってきた `channel`
  （`total` / `pi` / `deformation`）で UI の説明文と色が変わる。
  π の選択は `ScfResult::channels` を全部なめるので、UKS でも α/β 別々の軌道を見る
  （`DensityChannel::Pi` は `OrbitalRef { channel, index }` の列）。
- **差密度は符号付き。** `density::evaluate` は**負の値をクランプしない**（P3 の最初の版は
  していた）。`marching::extract_side(grid, level, Side)` で正負 2 枚の曲面を切り、
  Worker は 2 組のジオメトリを返す。
- **差密度は原子核の上で鋭く尖る。** CH₄ では炭素核で −2.2 e/Bohr³ に達する（分子と
  孤立原子の 1s カスプの差）。等値面の意味がある範囲はスライダーの下半分で、
  上のほうへ動かすと核まわりの赤い小球だけが残る。これは量の性質であって不具合ではない。

### P4 で分かったこと

- **開殻の参照値は `tests/data/scf_open_shell.json`。** `gen_reference.py` の
  `open_shell_reference()` が UKS（閉殻比較用の 1 件だけ RKS）で生成する。O₂ の三重項と
  一重項、CH₃・OH ラジカル、H/C/N/O/Al/Si 原子。α/β 別の密度行列と軌道エネルギー、
  `<S²>` まで入っているので、ずれたときにどの項が悪いか分かる。
- **PySCF 側も開殻原子は素直に収束しない。** 縮退した p 殻で DIIS が振動するので、
  `unrestricted_payload` は収束しなければ `mf.newton()`（二次収束法）に落とす。
- **`<S²>` は診断として効く。** `ScfResult::spin_squared(&overlap)` が
  `S_z(S_z+1) + n_β − tr(D_α S D_β S)`。三重項のつもりが一重項に落ちていても
  エネルギーはそれらしく見えるが、これは見逃さない。
- **level shift が無いと Al・Si 原子が解けない。** 3s と 3p が近く、占有/非占有が
  反復ごとに入れ替わる。**ダンピングでは直らない**（振動しているのは密度ではなく占有）。
  空軌道を持ち上げれば止まる。入れる前は Al が**カチオンとして**、Si が五重項として
  返ってきていた（どちらも中性基底状態ではない）。`tests/reference_open_shell.rs` の
  `a_level_shift_is_what_the_hard_atoms_need` が「無いと落ちる」ことごと固定している。
- **非収束を作るのは難しい。** 原子を重ねる・詰める程度では探索のどこかで収束する
  （O₂ を 0.4 Å、S 3 個の団子、C 4 個の積み重ね、いずれも収束した）。発散アニメーションを
  手で確認したいときは、Worker で `converged: false` を一時的に強制するのが早い。

### P4 の実測（自動探索のコスト）

閉殻分子は一重項と三重項の両方を解くので、単純に SCF が 2 回走る。
ネイティブ（release、`System::build` + 探索 vs `System::build` + 1 状態）:

| | 1 状態 | 探索 | 倍率 | 三重項の反復数 |
| --- | --- | --- | --- | --- |
| H₂O | 0.41 秒 | 0.53 秒 | ×1.30 | 7 |
| O₂ | 0.15 秒 | 0.28 秒 | ×1.91 | 7（採用） |
| NH₃ | 0.21 秒 | 0.57 秒 | ×2.65 | 10 |
| CH₄ | 0.26 秒 | 1.10 秒 | ×4.21 | **17** |
| ベンゼン | 5.28 秒 | 9.53 秒 | ×1.81 | 11 |

ブラウザ実測ではベンゼンが 16.5 秒 → **24.3 秒**。倍率が分子ごとに違うのは
三重項の収束の速さが違うから（CH₄ の三重項は 17 反復かかる）。
P6 でここを縮めるなら、三重項を**収束した一重項の密度から始める**のが素直
（`ScfOptions` に初期密度を渡す口を足す）。ギャップによる振り分けは上の規約のとおり不可。

### P3 の実測（ブラウザ、release + wasm-opt -O3）

初回の等値面（ρ サンプリング込み）: H₂O 0.12〜0.23 秒 / ベンゼン 1.0〜1.3 秒。
チャンネルごとに格子を 1 枚ずつ持つので、`total` と `bonding` の初回はそれぞれ 1 回かかる。
以降の閾値変更: H₂O 2 ms / ベンゼン 11〜17 ms。設計計画の「数 ms」を満たしている。
チャンネルを切り替えて戻ると、その格子は残っているので 12〜15 ms。
格子は `density::GridSpec::for_molecule`（0.22 Bohr 間隔・パディング 4 Bohr・上限 30 万点）で、
ベンゼンは 80×75×38 = 22.8 万点。ρ の格子積分は電子数に対して H₂O −2.5%、CH₄ +2.8%、
ベンゼン −1.8%（一様格子は核の尖りを解像できない。SCF が Becke グリッドを使う理由そのもので、
表示用としては十分）。初回の 1.2 秒はほぼ全部が ρ のサンプリングで、marching cubes 自体は
その 1/100 以下。P6 で縮めるならブロックごとの基底関数スクリーニング（XC と同じ話）。

### P2 時点の性能（P6 の出発点）

ブラウザ実測（release + wasm-opt -O3、SIMD なし・単一スレッド）:
H₂O 0.6 秒 / CH₄ 0.6 秒 / ベンゼン **16.5 秒**（8 反復）。

誤差は 2e-6〜5e-5 Ha。
