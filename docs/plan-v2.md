## P8 観測モード

読む dev-notes: 「規約の詳細」のうち viewer・アニメーション・Worker の項、「P7 の実装メモ」
（App を再マウントして確かめる方法）。

### 目的

講義中の誤操作（回そうとして原子を動かす、空いている所をクリックして原子を足す。
どちらも計算中なら計算が中止される）をなくし、距離・角度・二面角を画面で示せるようにする。

### 決めたこと

- **状態**: App に `mode: 'edit' | 'observe'`。viewer には `setMode()` で渡す。
- **編集モード**: 今の操作のまま（空いている所をクリックで配置、ドラッグで移動、
  Shift+クリックで隣接配置、Delete で削除）。
- **観測モード**:
  - 原子をクリック → 計測する原子に追加（もう一度クリックで外す）。最大 4 個で、5 個目は
    その原子から選び直し。
  - 原子の上から始めたドラッグも**回転**にする（原子を動かさない）。
  - 空いている所のクリック・Shift+クリック・Delete/Backspace は何もしない。Esc で計測を解除する。
- **測る値**: 2 個 → 距離（Å、小数 3 桁）、3 個 → 角度（2 番目に選んだ原子が頂点、度、小数 1 桁）、
  4 個 → 二面角（IUPAC の符号、−180〜180 度、小数 1 桁）。緩和で値が少しずつ変わるのが見えるように、
  桁は多めにする。
- **「結合の長さをすべて表示」トグル**: `findBonds` の組すべてに距離ラベルを付ける。
- **計測の寿命**: 原子の並び（数と元素）が変わる操作（追加・削除・全消去・プリセット・
  記録を開く）で消す。ドラッグで動かしたときと緩和では残し、値が追従する。
- **描画は viewer が持つ。** App は選んだ原子の番号列だけを渡す。値の再計算は
  `setMolecule` / `setPositions` の中で行う → アニメーション中（`FramePlayer` が
  `setPositions` を叩く）も値が動く。ラベルは three/addons の `CSS2DRenderer`
  （DOM を重ねる。`pointer-events: none`、`#resize` で同じ大きさに合わせる）。
  計測中の原子は、編集の選択とは別の色で強調し、原子どうしを破線で結ぶ。
- **緩和の前後**: 緩和を始めたときの構造を App が持っておき（`relaxedFrom`）、終わったら
  パネルに「前 → 後」（例: `1.540 → 1.512 Å`）を出す。記録を開いたとき（P9）は記録の初期構造を使う。
- **パネル**: 一番上に「編集 / 観測」の切り替え。編集モードでは「配置する元素」「編集」を、
  観測モードでは新しい「観測」の節（今の値と前→後、結合長トグル、計測の解除）を出す
  （パネルが縦に伸びすぎないように、モードで入れ替える）。操作説明の文もモードで変える。
- **自動切り替え（2026-09-20 ユーザー決定: 計算の開始時）**: 「安定な形にする」「この形のまま計算」を
  押した時点で観測モードにする（計算中の誤クリックで計算が中止されないように、また緩和中に
  値が動くのを計算中から見せられるように）。`solved` で終われば（時間切れの途中構造を含む）
  そのまま観測モード。発散・エラー・中止で終わったら、**開始前のモードに戻す**（直すのは
  編集なので。当初案の「失敗では切り替えない」と同じ結果になる）。ただし計算中にユーザーが
  自分でモードを変えていたら、そちらを優先して戻さない。

## 基底の差し替え（2026-09-20 提起 → **次のバージョンで検討**）

**決定（2026-09-20、ユーザー）: B（このバージョンは STO-3G のまま進める）。** 基底の差し替えは
v2 の路線（講義で使うための UI）と違うので、次のバージョンで改めて検討する。**このバージョンでは
記録を実際に貯める予定がない**ので、「あとで基底を変えると記録が比べられなくなる」という
P9 の前にやる理由も当てはまらない。下は次バージョンの足がかりとして残すメモ。

**きっかけ**: P8 で数値が見えるようになり、水の値が教科書と違うとユーザーが気づいた
（このアプリ 1.031 Å / 96.7°、教科書 0.957 Å / 104.5°）。実測は dev-notes
「基底と汎関数が構造に与える差」。要点だけ:

- エンジンは正しい（PySCF を同じ LDA/STO-3G で回すと小数 4 桁まで同じ）。ずれは**最小基底**のもの。
- **6-31G\* にすると角度はほぼ合う**（水 96.7° → 103.7°、実験 104.5°。アンモニア 100.7° → 106.0°、
  実験 106.1°）。汎関数（LDA）は角度の主因ではない。結合長には LDA の分が +0.01〜0.015 Å 残る。
- 分極関数（d）が要る。6-31G（d 無し）はアンモニアが平面になる。3-21G は分子によって当たり外れが大きい。
- 費用は要実測。PySCF の比ではベンゼンで時間 ×2.6 だが、我々は ERI を 8 重対称で全部持つので
  ベンゼンの `EriTensor` が 1.8 MB → 110 MB、力（ERI 微分）の四重項が 62 倍になる。
  小さい分子（水・アンモニア・メタン）は数秒に収まる見込み。
- 下地はある: 一般 l の Cartesian 基底、実行時 SAD、l=2 の積分の参照値（`integrals_h2o_631gs.json`）。

**P9 との関係**: P9 の記録は `model`（基底・汎関数・グリッド）を比較キーに持つので、基底を
変えると古い記録は同じ表に並ばない。実際に記録を貯めてから差し替えるなら、`model` の違う記録を
別の表に出す（P9 の決めごとのまま）か、作り直してもらうことになる。

**このバージョンでの扱い**: STO-3G のまま。角度が教科書より小さく出ることは講義で説明する
（「最小基底だと角度が小さく、LDA だと結合が長めに出る」は、それ自体が近似の話として使える）。
**2026-09-20 追記**: 加えて、**異性体どうしのエネルギーの順序を誤る**ことが分かった
（C₃H₆: アプリはシクロプロパンが 19.7 kJ/mol 低いと出すが、実験ではプロペンが 32.9 kJ/mol 低い）。
v2 では「同じ分子の形を比べる」用途に留める。実測は dev-notes「異性体のエネルギー順序も
最小基底で逆になる」。

### 次のバージョンで差し替えるなら（タスク案）

- [ ] `gen_reference.py` に 6-31G\* のテーブル生成を足す（`write_sto3g` と同じ形、Cartesian 6d）。
- [ ] エンジンの既定基底を切り替え、`cargo test` の参照値を作り直す（`scf_*.json` 全部）。

      （ベンゼンの `EriTensor` 110 MB がブラウザで通るか、最適化中に 2 つ生きることも含めて）。
- [ ] 必要なら対策を決める（グリッドを Medium に戻す + XC 重み微分、ERI の持ち方、
      `OPTIMIZE_BUDGET_SECONDS`、大きい分子の扱い）。
- [ ] `web/src/wasm/` を作り直してコミット、CI の作り直しを取り込む。
- [ ] 実測と判断を dev-notes に、状態を CLAUDE.md に。

## P9 安定構造の記録

読む dev-notes: 「規約の詳細」の F4・F5・Worker・アニメーションの項、「P6 の実測」
（収束後のエネルギーの桁）。`crates/dft-core/src/opt/mod.rs` の `Options`（収束判定）。

### 目的

「どこから始めたかで落ちる谷が違う」「どの谷が一番深いか」を比べられるようにする。
講義前に用意した構造を、教室ですぐに（計算なしで）開けるようにする。

**補足（2026-09-20）**: 講義で実際に記録を貯めるのはまだ先で、基底も v2 の間は STO-3G のまま
（「基底の差し替え」の節）。`model` の違う記録をどう扱うかで悩むより、まず動く形を作る。

### 決めたこと

- **何を記録するか**: 「安定な形にする」の結果のうち `hasUsableStructure()` のものを、
  **押すたびに自動で記録**する。一点計算は記録しない（安定な形ではないため）。
  削除・名前の変更・全部消す（確認つき）ができる。
- **順位に入れるのは収束したものだけ。** 時間切れ・回数上限のものは「途中」と表示して残すが、
  順位にも同じ谷の判定にも入れない。
- **比べてよい組（比較キー）= 組成（Hill 式）+ 電荷 + モデル。**
  - 電荷は、中性で解けなかったときに `driver` が ±1 を試すので、同じ原子の組でも違いうる。
    表示はしない（F4）。**規約の更新が要る**: CLAUDE.md の「`charge` は診断用」に
    「記録の比較キーとして内部で使う（表示しない）」を足す。スピン状態の違いは比べてよい。
  - モデルは `ENGINE_MODEL`（基底・汎関数・最適化グリッドを表す TS の定数。例 `sto-3g/lda-vwn5/fine`）。
    **基底や汎関数を差し替えたら変える**（これも CLAUDE.md の規約に足す）。モデルの違う記録は
    同じ表に並べない。
- **最適化の前に小さく揺らす（対称性を崩す）。**（2026-09-20、P9-1 の実測で確定）
  - 理由: 勾配は初期構造の対称性を保つので、対称な構造から始めると鞍点で「収束」しうる。
    **クリックだけで作った分子は、カメラを回さなければ全原子が同じ平面に乗る**
    （`#planePoint` は重心を通りカメラに向いた平面に置く）。**実際にそうなった**:
    平面の CH₄ は平面のまま収束し（正四面体より 834 kJ/mol 上）、平面の NH₃ も平面のまま
    （38.7 kJ/mol 上）。面外のずれは丸めではなく厳密に 0。
  - 方法: UI 側で、Worker に送る前に全原子を seed つき乱数で動かす（`records/perturb.ts`）。
    **振幅 0.05 Å**（球面上に一様な向き、全原子が同じ距離）。0.02 Å 以下だと面外の力が
    収束判定を下回って平面に戻ってしまう（実測: 0.05 Å で 9/9 脱出、0.02 Å で 2/3）。
  - **揺らすのは「平らで、かつ手で作った・編集した」構造だけ**（当初案の「例外を作らず
    常に揺らす」から変更）。揺らすと対称性の無い構造を収束させることになり、ベンゼンで
    3 歩 25 秒 → 15 歩 70 秒と高い（面外だけ揺らしても同じ）。一方、**揺らして得があるのは
    クリックが勝手に作る対称性＝平面に乗った構造だけ**で、プリセットや記録から開いた構造の
    対称性は分子自身のもの。平面でない構造・プリセットはそのまま送り、「すでに安定な形でした」も
    今までどおり出る。実測は dev-notes「P9 の実測」。
- **同じ谷の判定**: 比較キーが同じで、エネルギー差が閾値より小さいものは同じ谷としてまとめ、
  件数を出す。**閾値は 1 kJ/mol**（2026-09-20、P9-1 の実測で決定）: 同じ谷に落ちた結果の
  ばらつきは最大 0.03 kJ/mol（H₂O 0.0015、CH₄ 0.030）で、その 30 倍。講義で見せる差
  （エタンの回転障壁 ~12 kJ/mol、NH₃ の反転 39 kJ/mol）よりはるかに小さい。P9-3 で使う。
  鏡像どうしはエネルギーが同じなので同じ谷扱いでよい。
- **エネルギーの表示**: 同じ組の中で一番低いものを 0 とした相対値を kJ/mol で出す（詳細には Ha も）。
  **Hartree → kJ/mol の係数は記憶から書かない。** `scripts/gen_reference.py` に
  `scipy.constants` から書き出す関数を足し、その生成物（JSON）を web から読む。
- **記録を開く**:
  - 最終構造と、記録しておいた計算結果（`ScfOutcome`）をすぐ出す。パネルの数値は記録の値
    （= 最適化グリッドの値）のままにする。
  - 等値面には密度が要るので、前面の Worker で一点計算をやり直し、**密度だけ**使う
    （グリッドが違う一点計算のエネルギーで、表示の数値を上書きしない）。非収束なら等値面を出さないだけ。
  - 計算中のものがあれば中止する（編集と同じ）。観測モードにし、「前 → 後」は記録の初期構造で出す。
  - **「緩和を再生」ボタン**: 記録した軌跡を `FramePlayer` に流す。**流す前に `viewer.setMolecule()`
    で記録の元素・最初のフレームにする**（`setPositions` は今の原子の元素をそのまま使い、
    原子数の違うフレームは捨てるため）。最終構造は開いた時点で `setAtoms` 済みにしておく
    （規約「緩和後の構造は即 `setAtoms`」と同じ理由）。
- **保存**: IndexedDB（依存は足さず、薄いラッパーを書く）。保存層はインターフェースで切り、
  テストはメモリ実装で行う。IndexedDB が使えない環境（プライベートモードなど）でもメモリだけで
  動かし、「このブラウザには残りません。書き出してください」と出す。
- **ファイル**: JSON `{ format: 'mol-structure-log', version: 1, exportedAt, records }`。

## P10 並列探索

### 目的

講義中、前面の操作（表示・計測・等値面）を止めずに、いくつもの初期構造からの最適化を
同時に回し、結果を P9 の記録に流す。

### 決めたこと

- **エンジンも wasm も変えない。** Worker を複数立て、それぞれが今の `optimize` を呼ぶ。
  SharedArrayBuffer・COOP/COEP・nightly Rust は要らない。
- **前面の Worker（今の `clientRef`: アニメーション・等値面）とは別に、候補用のプール**を持つ。
  プールの大きさは `navigator.hardwareConcurrency` から前面の分を引いて決める（上限は P10-1 の実測で）。
- **候補の作り方**: (a)「今の形を候補に追加」（キューに入れる）、(b)「今の形から N 通り揺らして試す」
  （P9 の対称性を崩す揺らしより大きい振幅。値は実測で決める。原子が近づきすぎたら作り直す）。
- **結果**: 使える構造は `source: 'search'`・`batch` つきで記録へ入れる。軌跡も入るので、
  開けば前面で緩和を再生できる（背景で回した候補の動きを、あとから講義で見せられる）。
- **非収束の候補**（F5）: 数値も文言も出さず、行は「—」。開くと、その初期構造の発散アニメーションを流す。
- **中止**: 候補ごと・全部。これまでと同じく `terminate()` + 再生成。
- **時間の予算**: エンジンの `OPTIMIZE_BUDGET_SECONDS`（1800 秒）はそのまま。長すぎる候補は
  ユーザーが止める。JS 側で打ち切るかどうかは実測を見てから決める。

## 次のバージョン（v3）で検討すること

- **基底を 6-31G\* に差し替える**（上の節がそのままタスク案。実測は `docs/dev-notes.md` の
  「基底と汎関数が構造に与える差（2026-09-20 実測）」）。**v3 の筆頭候補**:
  講義で見せる数値が教科書に近づく効果がいちばん大きい。速度とメモリの実測から始める。
  **理由が 1 つ増えた（2026-09-20）**: 幾何（角度・結合長）だけでなく、**異性体のエネルギーの
  順序まで最小基底では逆になる**。C₃H₆ でシクロプロパンとプロペンを比べると、このアプリは
  シクロプロパンを 19.7 kJ/mol 低いと出すが、実験（NIST の ΔfH）ではプロペンが 32.9 kJ/mol 低い。
  6-31G 以上ならどの汎関数でも符号は正しくなる（dev-notes「異性体のエネルギー順序も最小基底で
  逆になる」）。**C₂H₆O（エタノール / ジメチルエーテル）でも同じく順序が逆**だった一方、
  **配座（エタンの回転障壁）は合う**。**v2 の間は、異性体どうしのエネルギー比較には使えない**と
  承知して使う（P9-9 参照）。
- スレッド並列（COOP/COEP + rayon）: 1 回の計算そのものを速くする。nightly Rust が要り、
  `rust-toolchain.toml` の固定や CI での再現ビルドと衝突する。基底を上げるなら一緒に要る可能性が高い。
- XC のグリッド重み微分を実装して最適化を Medium に戻す（ベンゼン最適化の 1〜2 割の見積もり）。
- `OPTIMIZE_BUDGET_SECONDS` の見直し。
- **汎関数も一緒に上げる（基底とセットで検討する）。** 当初は「結合長の残りのずれだけ」の
  話だったが、C₃H₆ の実測で **相対エネルギーには汎関数が大きく効く**ことが分かった:
  6-31G\* にしても LDA は異性体の差を −4.6 kJ/mol としか出さない（HF −33.7、B3LYP −31.8、
  実験 −32.9）。**基底だけ差し替えても異性体の比較は直らない**。PBE でどこまで届くかは未実測で、
  B3LYP（交換の一部が厳密交換 ＝ 実装は重くなる）まで要るかを含めて v3 で決める。

## 却下した案: WebGPU（2026-09-20）

- **WGSL に倍精度（f64）が無い。** 全エネルギー −227 Ha に対して比べたい差は 1e-5 程度（相対）で、
  SCF の収束判定や力の精度が単精度では足りないか、ぎりぎりになる。倍精度の模倣や
  単精度と倍精度の組み合わせは研究レベルの手間で、遅くなって利点を食う。
- **問題が小さい。** ベンゼンの STO-3G は基底関数 36 個。GPU 向きの大量の独立な仕事は XC の
  グリッド点くらいで、SCF は毎反復 CPU で対角化するため、そのたびに GPU と CPU の間を往復する。
- **時間が一か所に集まっていない**（下準備・探索・力・各ステップに分散。「P7 の実測」）。
- **検証の仕組みと合わない**（非同期・単精度では、素朴版と 1e-12 で照合する方式が使えない）。
  Claude の作業ブラウザは GPU が無効で、開発中に確かめられない。
- **環境の差が大きく**、CPU 版を残す必要があって実装が二重になる。
- 基底を 6-31G* に上げて問題が大きくなったら、改めて検討する価値はある。
