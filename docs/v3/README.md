## チケットにしていない候補（エンジン側、V3-8 の実測から）

どちらも「形を測る」のためのもので、やるかどうかは決めていない。数字は
dev-notes「v3 の実測」。

- **電子の並び方を「形を探す」の基底で選び、勝った状態だけ 6-31G\* で解き直す。**
  ベンゼンを測るときの待ちの 1/3〜2/3 は、画面に出ない三重項の試行（6-31G\* で 52 回、
  シクロプロパンでは 100 回回っても収束しない）。一点計算が 71 秒 → 約 15 秒、緩和が
  176 秒 → 約 2 分の見込み。規約の「一重項と三重項を両方解いて比べる」は小さい基底の中で守れる。
- **試しの構造を組む前に、今の構造の ERI を捨てる。** 緩和の 1 歩では ERI が 2 本
  （ベンゼンで 105 MiB × 2）同時に生きているため、線形メモリが歩数とともに増える
  （ベンゼンを測ると 420〜625 MiB）。

## チケットを終えるときにやること

1. **この板の状態を書き換える**（1 行）。
2. **実測・却下した案・数字の出どころは dev-notes の「フェーズの記録」に 1 節**足す。
   チケット本文には書かない（チケットは着手のための紙で、記録ではない）。
3. **規約が増えたら CLAUDE.md に 1〜2 行**。増えていないなら触らない。
4. コミットはユーザーに言われたときだけ。

## 全チケットに共通する前提

- **単位**: エンジンは Bohr/Hartree、UI は Å。変換は `dft-wasm` の境界だけ。
- **F4**: 画面に基底・汎関数・電荷・多重度を出さない。段の名前も目的の言葉だけ。
- **`web/src/wasm/` は生成物だがコミットする**（`npm run build:wasm`）。Rust を触ったら忘れない。
- テストは `cargo test --workspace` と `npm test`（web）。
