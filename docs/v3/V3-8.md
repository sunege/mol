# V3-8 速さとメモリの実測、予算の見直し

**依存: V3-4〜V3-6（画面から両方の段が回せるようになってから）**

**目的**: 「形を測る」が実際に何秒でどれだけメモリを食うかを測り、**文言の「数十秒〜数分」と
予算の定数を実測で決める**。

## 前提

- **時間の比較は Node で取る**（`--target nodejs` の release を小さなスクリプトから呼ぶ）。
  Browser ペインは非表示だと間引かれ、この機械（2 物理コア）は同じバイナリでも **±30% ぶれる**
  ので、**複数回の最小値**で判断する。手順は dev-notes「コマンドの詳細」。
- ネイティブの見積もり（v3-0、1 歩あたり）: 水 ×2.0、CH₄ ×1.8、C₃H₆ ×4.6、**ベンゼン ×8.1**。
  ベンゼンはブラウザで 15 秒 → **2 分前後**の見込み。
- ERI テンソル: ベンゼンで 1.7 MiB → **105 MiB**。Worker 1 本は 139 MiB → **250 MiB 前後**の見込み。
- 予算の現状: エンジン側 `OPTIMIZE_BUDGET_SECONDS = 1800`、候補 1 本の `budgetMs = 10 分`。

### V3-4 で入ったもの（2026-09-22）

- **直す文言の場所**: `web/src/components/level.ts` の `WORDS` の `time`（`'数秒'` と
  `'数十秒〜数分'`）。`levelHint()` が「…ための計算です。かかる時間の目安は○○です。」に
  組み立て、`level.test.ts` が 2 つの文を丸ごと固定しているので、テストも一緒に直す。
  「精度」「正確」などの語と F4 の禁止語（`6-31G` を含む）はテストで弾かれる。

## やること

1. Node で、両方の段の**ベンゼン・C₃H₆・水**の「安定な形にする」を 3 回ずつ測り、最小値を取る。
   **段階ごとの内訳**（下準備・電子の並び方・1 歩）も P7 の表と同じ形で取る。
2. **Worker の線形メモリ**を両方の段で見る（nodejs グルーの末尾に
   `module.exports.__wasm = wasm;` を足す手。dev-notes「コマンドの詳細」）。
3. `OPTIMIZE_BUDGET_SECONDS`（1800 秒）と候補の `budgetMs`（10 分）が、
   **「形を測る」でも妥当か**を判断する。変えるなら理由を dev-notes に書く。
4. **V3-4 の文言（時間の目安）を実測で直す。**
5. 「形を測る」で**大きい分子を選んだときに事前に知らせるか**を決める。
   （ユーザーの判断: 長さは既存の時間切れの道に任せる。**知らせるとしても止めない**。）
